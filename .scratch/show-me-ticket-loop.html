一句话理解

Ticket Loop 是一个串行、可审计、可恢复的本地工单执行器。它冻结一组 Markdown 工单，按依赖选择下一张票，为每张票创建独立 Claude Code Session，并用 Git 与工单证据而不是模型自述判断是否完成。

1 ×任一时刻仅执行一张票
2implementation / closeout 两阶段
2 ×每阶段最多两次 resume
74当前测试方法数量
核心可靠性原则

Claude 返回退出码 0 或文本声称“已完成”都不算完成。只有分支、提交历史、工作区、Checklist、Status 与 Completion evidence 全部通过硬校验，调度器才会进入下一张票。

Supervisor 做什么？

固定执行 plan → start → step/resume，持续到 completed 或终止状态。每轮严格服从 Runner 返回的 allowed_actions，不会自行猜测下一步。

常用参数

参数用途默认 / 约束
--model指定 Claude 模型省略时继承用户 Claude Code 配置
--implement-command覆盖实现 Skill 名称自动寻找 namespaced implement，找不到回退为 implement
--implementation-timeout首次实现调用超时5400 秒
--closeout-timeout首次收口调用超时1800 秒
--resume-timeout恢复调用超时1800 秒
--max-cost-usd下一次调用前的累计成本门限正数；不是单次调用硬上限

工单必须长什么样

文件名必须是两位编号 01–99 开头；Task Ticket 至少包含三个字段。依赖只从 Blocked by 字段解析，不从正文推断。

# 02 — Add API client

**What to build:**
实现 API client，并添加单元测试。

**Blocked by:** 01-foundation.md

**Status:** ready-for-agent

## Acceptance checklist
- [ ] Client handles success responses
- [ ] Client handles timeout errors
- [ ] Typecheck passes

可执行 Task Ticket

  • 文件名匹配 01-title.md
  • Status 为 ready-for-agent 或合法 done (...)
  • Blocked by: None 或引用存在的工单
  • 不得有重复 ID、自依赖或依赖环

Wayfinder 只作为依赖

  • 只要存在 Type:，即被分类为 Wayfinder
  • 允许类型：research、prototype、grilling、task
  • 状态仅接受 claimed / resolved
  • 即使 Type: task 也不能被 --tickets 执行
Plan 成功不等于可启动

外部 blocker 尚未完成时，plan 仍可成功但 frontier 为 null；真正 start 时会以 frontier-empty 拒绝运行。

03

运行机制

Supervisor 是薄控制层，Runner 才是事实来源。Runner 冻结 Manifest、维护 Ledger、启动 Claude 子进程，并在每次调用后执行确定性门禁。

01

Plan：解析并冻结

检查工单格式、依赖、外部 blocker，生成 Manifest；此阶段不调用 Claude。

02

Start：建立运行上下文

验证 Git 仓库、分支、干净工作区和锁，记录起始 HEAD、运行参数与第一张 frontier ticket。

03

Implementation：新 Session

为工单生成 UUID，首次 prompt 严格为 /<implement-command> @<绝对工单路径>。

04

Closeout：复用同一 Session

要求校验 Checklist、写 Status 和 Completion evidence；必要时仅允许一个精确命名的收口提交。

05

Advance：选择下一张票

从 Manifest 中选择编号最小、依赖全部满足的 ready ticket；运行中新增的文件不会被吸收。

05

两阶段完成门禁

Phase A

Implementation 必须证明代码已落地

  1. Claude 返回的 session_id 同时匹配 Ledger 和当前 ticket 映射。
  2. 工作区完全干净。
  3. HEAD 相比 ticket start HEAD 前进。
  4. ticket start HEAD 仍是当前 HEAD 的祖先，历史未被改写。

通过后，Runner 记录 implementation_head，进入 closeout。

Phase B

Closeout 必须证明工单已收口

  1. 所有 Acceptance checklist 均已勾选。
  2. Status 为 done (日期, implementation commit)。
  3. 恰好一个 Completion evidence，包含 Implementation、Typecheck、Tests、Review。
  4. 若有收口提交，只能新增一个，且主题精确为 chore(ticket-loop): close <ticket-id>。
  5. 收口提交只能修改当前 ticket。
证据文本也会被校验

Not applicable 必须附括号原因；evidence 中未被否定解释的 fail、error、broken 等失败词会导致拒绝。

06

持久化、锁与崩溃恢复

运行数据放在哪里

.ticket-loop/
├── runs/<run-id>.json                 # Ledger：状态、HEAD、尝试、成本、恢复快照
└── logs/<run-id>/
    ├── <NN>-<phase>.json              # Claude 原始 stdout
    └── <NN>-<phase>.stderr.log        # Claude stderr

<git-common-dir>/ticket-loop/
├── command.lock                       # mutation command 的 flock
└── lock.json                          # 当前 run 的所有权与 PID/PGID

Runner 将 .ticket-loop/ 写入 Git 的本地 info/exclude，不会修改项目 .gitignore。Ledger 使用临时文件、fsync 和原子 replace 写入；目录权限为 0700，文件为 0600。

失败如何恢复

A

普通 gate failure

记录 HEAD、porcelain status 与内容 fingerprint，保持 running，下一动作变为 resume。

B

恢复前校验现场

若任何文件内容、分支或历史发生漂移，拒绝 resume，避免在错误上下文继续。

C

复用原 Session

Runner 使用 --resume <session-id>，提示只修复当前 gate，不得开始下一票。

D

恢复额度

implementation 与 closeout 各自最多两次 resume；额度耗尽转为 terminal-failure。

SIGKILL / Runner 崩溃不是盲目重跑

若 child 尚未 spawn，可清理 stale lock 后重试 initial call；若已 spawn，先验证并终止残留进程组，再转为 interrupted，必须显式 reopen 后恢复原 Session。

07

观察、停止、重开与清理

需要细粒度控制时，可绕过 Supervisor 直接使用 Runner。以下命令中的路径以已安装 Skill 目录为例。

RUNNER="${CLAUDE_SKILL_DIR}/scripts/ticket_loop.py"

python3 "$RUNNER" plan   --issues-dir .scratch/feature/issues --range 01-07
python3 "$RUNNER" start  --tickets path/to/01.md path/to/02.md
python3 "$RUNNER" step   --run <run-id>
python3 "$RUNNER" resume --run <run-id>
python3 "$RUNNER" status --run <run-id>
python3 "$RUNNER" reopen --run <run-id>
python3 "$RUNNER" abort  --run <run-id>
python3 "$RUNNER" clean  --run <run-id>
命令会调用 Claude？关键行为
status否只读公开状态、当前 ticket/session、尝试次数、调用、成本、gate failures
abort否终止活动进程组，状态置为 aborted；不 reset/stash/delete 业务改动
reopen否重新验证仓库、分支、祖先关系、恢复 fingerprint 与 Session 身份，再回到 running
clean否仅删除该 run 的 Ledger 与日志；只允许 completed / aborted
step至多一次推进正常阶段
resume至多一次在现场未漂移时恢复原 Session
重新调用一键 Skill 不会接管旧 run

Supervisor 总是先 plan → start；已有 run 会让新 start 受仓库锁阻止。只有直接 Runner 的生命周期命令在省略 --run 且恰好存在一个未完成 run 时，才会自动选择它。

清理故障 run

terminal-failure 或 interrupted 不能直接 clean。若决定放弃，先执行 abort，再执行 clean。

CLI：ticket_loop.py:1768-1854 · status：ticket_loop.py:701-723 · abort/reopen/clean：ticket_loop.py:1634-1734

08

Claude Session 与无人值守执行

是的，Ticket Loop 使用 Claude Code CLI 的 print 模式发起 Session：源码写的是长参数 claude --print，等价于常说的 claude -p。它不是交互式 TUI，而是执行一次 prompt，等待 JSON 结果后退出。

首次 Implementation：创建 Session

claude \
  --print \
  --output-format json \
  --permission-mode bypassPermissions \
  --dangerously-skip-permissions \
  --append-system-prompt "$UNATTENDED_CONTEXT" \
  [--model "$MODEL"] \
  --session-id "$SESSION_ID" \
  "/$IMPLEMENT_COMMAND @$ABSOLUTE_TICKET_PATH"

每张新工单生成一个 UUID Session。--model 仅在启动参数显式指定模型时出现；首条 prompt 严格为 /<resolved-command> @<ticket-absolute-path>。

Closeout 与恢复：继续原 Session

claude \
  --print \
  --output-format json \
  --permission-mode bypassPermissions \
  --dangerously-skip-permissions \
  --append-system-prompt "$UNATTENDED_CONTEXT" \
  [--model "$MODEL"] \
  --resume "$SESSION_ID" \
  "$CLOSEOUT_OR_RECOVERY_PROMPT"

Implementation、Closeout 和故障恢复复用同一张票的 Session。Runner 还会验证 Claude JSON 返回的 session_id 同时匹配 Ledger 与当前 ticket 映射；不匹配时进入不可 reopen 的 claude-session-mismatch。

实际进程还有一层 Child Launcher

python ticket_loop.py __child-launcher <control-fd> \
  claude <上述完整参数...>

Launcher 先等待控制管道。Runner 得到 PID/PGID 并把 in_flight=spawned 写入 Ledger 和运行锁后，才向管道写入 1，随后 Launcher 通过 execvp 真正执行 Claude。这避免 Runner 崩溃后出现“Claude 已启动，但账本不知道它是谁”的孤儿进程窗口。

如何降低中途询问造成的中断

01

非交互调用边界

--print --output-format json 不启动交互式 Claude Code TUI，Runner 捕获 stdout/stderr 并等待单次调用结束。

02

跳过工具权限确认

--permission-mode bypassPermissions 与 --dangerously-skip-permissions 避免文件修改、测试和 Git 工具弹出审批。这也移除了权限保护，只能用于可信执行面。

03

无人值守系统提示

工单、Testing Decisions、验收标准与既有测试边界视为预先授权；对纯本地、可逆、低风险且可从现有惯例推导的选择，采用推荐默认、记录假设并继续，不等待用户确认。

04

门禁失败自动 Resume

若 Claude 只输出问题而未完成提交，Runner 会从无提交、脏工作区或 evidence 不完整等硬门禁识别失败，随后 Supervisor 使用原 Session 自动 resume。

05

超时终止进程组

Implementation 默认 5400 秒，Closeout/Resume 默认 1800 秒；超时先 SIGTERM，1 秒后仍未退出则 SIGKILL，并保存日志进入恢复路径。

并非所有问题都应自动决策

遇到不可逆决策、凭据或生产环境、网络发布、push/PR、Git 历史改写、超范围删除，或不同选项会实质改变交付且无法安全回退时，系统提示仍要求 Claude 停止并报告。这是安全边界，不应通过更强提示词消除。

当前仍可加固：关闭继承的 stdin

当前 subprocess.Popen 捕获了 stdout/stderr，但没有显式设置 stdin，因此 Launcher/Claude 理论上仍继承 Runner 的标准输入。严格无人值守边界可增加：

process = subprocess.Popen(
    launcher_command,
    cwd=str(ledger["repository"]),
    stdin=subprocess.DEVNULL,
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
    text=True,
    start_new_session=True,
    pass_fds=(control_read,),
)

stdin=DEVNULL 可使意外读取终端输入的代码立即得到 EOF，而不是悬挂等待；但它不能阻止模型在最终文本中提出澄清问题，后者仍依赖明确工单、Testing Decisions、无人值守提示、硬门禁和原 Session resume。

推荐在工单中补充 Testing Decisions

## Testing Decisions

- 使用仓库现有测试框架，不引入新框架。
- 采用相邻模块的 mock 方式。
- 允许新增本地 fixture，不访问生产服务。
- 不要求 push 或创建 PR。
- 多个等价且可逆的实现中，采用与相邻模块一致的方案并继续。
最稳妥的无人值守组合

明确工单 + Testing Decisions + --print + bypassPermissions + unattended system prompt + 超时 + Git/工单门禁 + 原 Session resume；建议再补充 stdin=DEVNULL。

09

安全边界

这是高权限无人值守执行，不是沙箱

任务 Session 以 bypassPermissions 与 --dangerously-skip-permissions 运行。Git 门禁只能验证仓库结果，不能阻止恶意命令、凭据读取或仓库外副作用。

Runner 追加的无人值守系统上下文允许本地源码、测试、ticket 状态和本地提交，但要求在凭据、生产环境、网络发布、push/PR、历史改写、超范围删除或不可逆决策处停止。这是行为约束，不是操作系统级隔离。

仅在可信执行面使用

  • 可信仓库与项目指令（CLAUDE.md）。
  • 可信插件、Skills、hooks 与 MCP servers。
  • 可信构建脚本和依赖安装行为。
  • 明确接受本地日志长期保留源码片段、命令输出和路径。

成本门禁的真实语义

--max-cost-usd 在每次调用前检查累计成本。若调用前尚未达到上限，该次调用仍会开始，因此最终累计成本可能超过门限；若成本字段未知且配置了上限，则 fail closed。

限制、边界条件与易错点

平台：当前实现面向 POSIX
代码直接依赖 fcntl.flock，适用于 macOS/Linux；Windows Python 不能按当前实现直接运行。
只支持串行，不支持并行或多 worktree 分发
任一时刻只处理一张票；不会自动创建分支、worktree 或 clone，也不会 pull、push、PR、merge、rebase、cherry-pick、stash、reset。
外部 blocker 在运行中不可变
外部 blocker 的路径、状态、kind 与 SHA-256 被冻结。运行中人工完成或修改它会被视为漂移并触发 terminal failure；应重建 run，或一开始就把 blocker 纳入 Manifest。
预先 done 的 ticket 校验弱于本次完成的 ticket
Manifest 中预先标为 done 的 ticket 会直接进入 completed 集合，不会执行本次 closeout 的完整 evidence 与 commit 存在性校验，因此其真实性仍依赖生成者或人工保证。
人工“顺手修复”可能破坏恢复
普通失败后，Runner 会冻结 Git snapshot 与文件内容 fingerprint。外部人工修改即使正确，也可能触发 recovery-context-drift；这是有意的 fail-closed 设计。
Session mismatch 不可 reopen
Claude 返回的 session ID 与 Ledger / 当前 ticket 映射不一致时，身份链已不可信，只允许 status 或 abort。
日志不会自动清理
原始 Claude JSON 和 stderr 会持续保留；它们可能含源码片段、命令输出、路径和 ticket 内容。成功后也必须显式 clean。
测试覆盖广，但本报告未重新执行测试
当前测试文件有 74 个 test_... 方法，使用真实临时 Git 仓库与 fake Claude executable 覆盖进程边界；本报告基于只读代码审阅，没有重新运行测试。
