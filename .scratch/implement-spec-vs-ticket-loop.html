同样面对一个目录中的 Ticket 任务图，implement-spec 追求并行交付 PR，ticket-loop 追求串行、可恢复地完成本地提交。关键不是谁绝对更强，而是谁把你最在意的失败模式管住。

结论先行

两者不是同一层级的实现：ticket-loop 是有代码、有账本、有状态机和行为测试的 workflow runtime；implement-spec 是交给主 Agent 执行的多 Agent 编排规程。前者牺牲吞吐量换确定性，后者牺牲确定性换并发与完整 PR 生命周期。

ticket-loop

更像可靠的本地执行器

冻结 Manifest，串行选择 frontier，用 Git、Ticket 内容和 Session ID 做硬门禁；中断后可验证现场并恢复原 Session。

胜在：恢复、审计、无人值守、确定性。
implement-spec

更像并行交付作战手册

主 Agent 理解任务图，给每张可运行 Ticket 分配独立 worktree/branch，再由 merger 汇总到 draft PR。

胜在：吞吐、隔离、PR 交付、跨票集成审查。
综合判断

如果问题表述只是“把这个目录里的 Ticket 可靠做完”，默认选 ticket-loop。如果问题表述是“尽快把一个宽而浅的任务图变成可审查 PR”，再选 implement-spec。

03

各自的优势与代价

ticket-loop / strong points

为什么它更可靠

  • 控制平面是代码。 Claude 负责实现，Runner 负责决定能否推进。
  • 失败是一级状态。 Gate failure、interrupted、terminal-failure、aborted 都有明确动作集合。
  • 恢复不靠猜。 先比较分支、HEAD、status 和内容 fingerprint，再恢复精确 Session。
  • 范围不会漂移。 启动时冻结 Manifest，运行中新增 Ticket 不会被悄悄吸收。
  • 审计链完整。 Ledger、原始 Claude JSON、stderr、提交和 Ticket evidence 可追溯。

它为此付出的代价

  • 所有 Ticket 串行，一个慢票会阻塞整条链。
  • 没有 worktree/branch 隔离，半成品留在当前工作区。
  • 不负责 draft PR、push、merge 或 ready-for-review。
  • Completion evidence 是结构门禁，不等同于 Runner 独立重跑测试。
  • 依赖 POSIX 锁和进程组，不是跨平台实现。
implement-spec / strong points

为什么它更快、更像交付流程

  • 利用宽 frontier。 无依赖 Ticket 可同时实施，显著缩短 wall-clock。
  • 文件系统隔离。 每个 implementer 有自己的 worktree 和 branch。
  • 交付终点明确。 从 draft PR 开始，以 ready-for-review 结束。
  • 上下文传播克制。 通过 spec、ticket、研究笔记和 commits 传递事实。
  • 有集成视角。 全部合并后统一 code review，可发现跨票问题。

它尚未定义的关键能力

  • 没有持久的 Ticket → Agent → worktree → branch → merge 映射。
  • 没有并发上限、timeout、重试预算或成本门限。
  • 没有 merge queue、冲突升级和过时 base SHA 策略。
  • 没有主 Agent 中断后的恢复或孤儿 worktree 清理协议。
  • review 后只规定一次 fix，没有要求复审到零阻塞项。
关键差别：implementer 不是 /implement 的同义词

ticket-loop 会在 Runner 中固定构造 /implement @<ticket>，因此每张票都进入统一的 implementation、closeout、测试与提交流程。implement-spec 只要求启动名为 implementer 的 subagent，并没有规定它必须调用 /implement；实现方式、测试、review、commit 和完成证据主要依赖主 Agent 与 subagent 自行遵循。

因此，implement-spec 的并行能力之外还存在一个流程一致性风险：不同 implementer 可能采用不同实现纪律。若要补齐，应明确要求每个 implementer 执行 /implement @ticket，只在自己的 worktree/branch 中工作，并返回 implementation commit、测试结果、review 结果和剩余 blocker。

成功路径上，两者都可能完成代码；当 Claude 超时、分支漂移、实现只做了一半、主 Session 中断或 merge 冲突时，才会看见系统设计的成熟度。

它以跳过工具权限确认的方式运行任务 Session。Git 门禁能保护仓库结果与恢复现场，却不能阻止恶意脚本、凭据读取或仓库外副作用；只能在可信仓库、Skill、Hook、MCP 和依赖链上使用。

05

两者的质量闭环都还差最后一步

逐票闭环

Ticket Loop

每票调用 /implement，随后 closeout 校验 Checklist、Status、Implementation commit 与 Typecheck / Tests / Review evidence。强项是流程证据可机器检查。

缺口：Runner 本身不重新运行项目测试，也不证明 review 的语义质量；文本 evidence 仍可能只是声明。

集成闭环

implement-spec

所有 Ticket 合并后，在 PR branch 统一运行 /code-review，再由一个 implementer 修复 findings。强项是能看到跨 Ticket 的集成结果。

缺口：没有规定修复后再次 review，也没有机器 Gate 证明所有阻塞 findings 和集成测试已清零。

更完整的标准应是

逐票局部验证 → merge 后集成测试 → PR 级 code review → 集中修复 → 再次 review → 零阻塞项且测试通过后才 ready。

06

按任务特征选择，不按工具名选择

依赖紧密、基本线性

选 ticket-loop 后一票必须消费前一票的真实代码，串行反而减少返工和合并不确定性。

宽而浅、模块边界清楚

选 implement-spec 并行收益明确，且不同 Ticket 很少触碰相同文件和公共抽象。

夜间 AFK / 长时无人值守

选 ticket-loop Ledger、锁、原 Session 恢复和硬门禁比并发速度更重要。

最终必须直接形成 PR

选 implement-spec 它原生覆盖 branch、draft PR、merge、review、ready 与 worktree 清理。

预算严格、资源受限

选 ticket-loop 有累计成本、timeout 与有限重试；implement-spec 的最大并发可能放大 token、CPU 和测试资源消耗。

不允许远程副作用

选 ticket-loop 它明确不 push、不建 PR；implement-spec 的 draft PR 是核心步骤。

当前工作目录不能被占用

选 implement-spec 独立 worktree 更适合与人的当前工作并存。

隐含依赖很多、Ticket 质量一般

优先 ticket-loop 先接受较慢的串行，直到任务图和模块边界足够可信再引入并发。

07

最佳长期方案：确定性控制面 + 有界并行

若要演进项目能力，最值得做的不是让其中一个完全取代另一个，而是把 Ticket Loop 的“可恢复控制面”与 implement-spec 的“worktree 隔离和 PR 交付面”组合起来。

保留 Ticket Loop 的部分

  • Versioned Manifest 与机器依赖检查
  • 冻结运行范围与确定性 frontier
  • 持久 Ledger 和 allowed-actions 状态机
  • Git / Session identity gates
  • timeout、retry、cost、abort、reopen、clean

引入 implement-spec 的部分

  • Run 使用专用 PR branch/worktree
  • frontier Ticket 使用独立 worktree/branch
  • 默认并发 2–3，而不是“最大并发”
  • 持久化的串行 merge queue
  • PR 级集成测试、review、fix、复审

建议的最小增强顺序

  1. 先给 implement-spec 增加持久 run ledger，记录 Ticket、Agent、worktree、branch、base SHA 和 merge commit。
  2. 把“maximum concurrency”改成有上限的 frontier 并发；一般仓库默认 2–3。
  3. 所有 merge 串行化，并在每次 merge 后运行相关集成测试。
  4. 定义冲突、超时、Agent 退出和主 Session 中断后的可恢复状态。
  5. review 修复后必须复审；只有零阻塞 findings 才能将 PR 标记 ready。
  6. 最后再考虑让 Ticket Loop 支持可选 PR 模式，而不是先破坏其简单、可靠的串行内核。
