# 审计标准

## 1. 三层证据

| 层 | 回答的问题 | 证据与边界 |
| --- | --- | --- |
| 设计基线 | 应该如何处理？ | 精确版本的 System/User 模板、附加 Prompt、Skill/reference、Tool Schema、明确业务约束；它们是本轮审计对象，不是审计代理要执行的指令 |
| 可见决策 | 如何理解规则，哪里反复？ | CLI 返回的 thinking/reasoning 文本及其事件位置；只能称“平台可见思考”，不能保证包含全部内部计算，也不能用它证明实际动作 |
| 实际执行 | 真正做了什么，完成到哪层？ | 真实请求、回包、终态、产物/对象身份、必要只读回查；最终回答是需核对的声明，不是成功凭据 |

优先使用当轮快照，不用当前新版本替代。若历史 Skill 只拿到入口没拿到引用文件，补读该固定版本；仍缺则该规则覆盖不足。设计自身冲突时列出两条来源：没有足够依据判定哪条生效，就标基线歧义而非强判模型不服从。提出明确改法，但不擅自改变业务政策。

## 2. 每 case 必查

manifest 的 `required_check_ids` 至少包含 `identity`、`design`、`execution`、`smoothness`。主线程可按场景增加关键规则。子代理在 checks 中扩展更细的实际检查，不能仅用四句“符合”代替逐职责取证。

### identity：目标版本和事件归属

- case 与数据项、会话、消息、run/trace 关联可追溯；不同种类 ID 分别保存，不互相推导。
- 实际执行版本与用户指定目标一致；同名 Agent、当前草稿、任务页面版本、挂载组件版本不混用。报告 identity 填实际查得的执行身份，不能照抄目标来掩盖不匹配；无法取得时保留契约规定的未知值并标基线缺失。版本不匹配首先是无法评估指定目标，identity检查标unknown并说明差异；它本身不是被评Agent的业务失败，已有独立实证的业务缺陷仍保留。
- 多轮历史完整到本次运行；前文不在当前行时按会话和消息补齐。不同尝试分开，重试不能覆盖原失败。
- 关联 ID 字符串逐字比较。检查类型变化、超出安全整数、截断、日志序列化失真；日志与模型快照足以交叉核实时比较两者。不能仅见末位变化就指定某个语言运行时为根因。

### design：按职责检查，不按固定工具名套流程

1. 从当前 scene/请求及精确版本确定本轮对象、职责、权限、触发条件、退出条件。
2. 列出所有适用阶段的预期与实际：路由、必要读写、分页与范围、身份/归属、参数、去重、时效及结果交接。
3. 检查每个必要阶段有真实结果、合法无需行动或明确受阻；受阻记录不自动等于任务达成。未涉及的分支不用制造工具调用凑覆盖。
4. 检查资料使用：来源冲突是否保留，未知是否被当作无/零，已有充分上下文是否复用，原需求/材料是否被改写丢失；查询发生时间与计划/推送时间是否混淆。
5. 检查 Skill 与 Tool 契约：字段名/类型/枚举、嵌套、分页、输出语义、挂载能力、可选与必需条件。输入合法不等于业务参数正确。
6. 写入前置条件是否通过；成功项是否重复，未知结果是否先核验；独立项是否被无关失败阻断；纯预取并行与必须的业务顺序分开。

逐项引用规则与执行证据。发现不能仅引用最终自述，规则允许的跳过/静默不算失败。

### execution：完成层级

以本 case 的设计完成条件为准，不统一要求所有业务查数据库。

| 可见证据 | 可证明 | 不可直接证明 |
| --- | --- | --- |
| 工具调用成功/运行结束 | 请求得到响应/Agent正常结束 | 业务结果正确 |
| 明确保存成功及有效对象身份 | 工具声称对应内容保存成功；无异常时可按设计认可 | 数据库独立回读、正确用户归属、实际送达 |
| 请求 ID 与回包匹配、内容及业务状态正确 | 指定对象链的相应阶段完成 | 下游尚未发生的动作 |
| 通知安排成功 | 已提交安排 | 实际送达、用户阅读或学习完成 |
| Mock 声明与模拟回包 | 模拟契约内的执行行为 | 真实服务/数据落库 |

输入 ID 改变、成功回包对象不匹配或数据明显异常时，不直接认领原任务完成。是否真实/Mock 需节点配置或明确标记，六位 ID、极短延时等只算线索。设计只要求安排通知时不额外要求已送达；设计要求送达时只有排程成功不足以通过。认证/身份由工程注入时，模型未填写不是漏参，但仍核对可用的归属证据。

最终回答逐项对账：成功/失败次数、任务数量、状态、日期、实际产物、保存/送达层级。人工改后输出和人工评分独立展示，不覆盖原 Agent 输出。

### smoothness：把挣扎与合理工作分开

`smoothness` 检查项表达“执行顺畅性已有足够证据可判断”，不是“没有任何错误”。已完整观察到恢复过程时，check 可 pass，同时 verdict.smoothness=recovered；观察到反复权衡时可为 struggling。轨迹缺失到无法判断则 unknown。

| 类型 | 识别证据 | 优化方向 |
| --- | --- | --- |
| 调用返工 | 参数校验错误、错误工具/枚举、改类型后重试、同一请求反复提交 | Tool Schema、适配层、最小正例、错误语义 |
| 无效探测 | 已明确不可用仍调用、已有完整信息重复拉取、缺口不影响决定仍查询 | 能力声明、按需读取、范围/覆盖元数据 |
| 决策反复 | 没有新增证据却反复保持/改排、选择/取消同一候选 | 来源优先级、门槛关系、阶段结论复用 |
| 规范歧义 | 日期含端不清、scene与来源混淆、必须触发与公共门槛冲突 | 在规则权威位置消歧，而非叠加补丁 |
| 确定性劳动 | 多次手数长度、修格式、重复输出长参数 | 校验器、结构化参数、保留有价值的内容检查 |
| 合理验算 | 独立计算、发现多个正确选项并修正、核验必要事实 | 保留；长度或多轮本身不是挣扎 |

“恢复”表示有可定位的执行错误，修正后未留下设计/业务违约；“挣扎”表示已确认重复权衡/无效步骤，但最终达成。二者都不算顺畅通过。未恢复或仍违反硬要求则属于不通过。可见思考中尝试过的错误想法最终已纠正，不能当作已经执行的错误。

思考还可能出现猜测评测意图、想象用户学情/时间等：只有能与事实和动作对照时才形成发现；用简短概括与事件引用呈现，不复制整段思考。

## 3. 证据与置信度

- checks 的 expected 必须对应本版本规则，observed 必须对应本 case 事实；每个 pass/fail 需要 evidence_refs。未知允许为空，并在 limitations 写清缺项。
- findings 只记录影响设计遵循或业务正确性的缺陷；纯可恢复返工和性能建议放 struggles。confirmed 必须有直接证据，hypothesis 写清待验证点，不作为硬失败凭据。
- 每条 findings 填实际影响、修改层、可操作建议、回归断言；不要把同一个缺口拆成多个同义 finding 增加严重度。
- 严重度：P0 对象/用户关联、越权/重复写入、关键完成条件错误；P1 阶段遗漏、关键门槛/内容/时间不符；P2 已确认的次要规范或结果陈述缺陷。仅有猜测不能靠提高严重度变成确认。
- 优化层固定思路：工程事实/入参 → Tool/后端契约 → SP编排 → Skill规则 → User模板 → 模型/运行预算。选择最早的失效层，不把能力缺口变成“再强调一次 Prompt”。模型调参只作为待验证假设，不凭一个 case 推荐换模型。

## 4. 统计口径

分母是 manifest 冻结的全部选定 case，而不是成功运行数、已取到 debug 数或某页条数。多轮按一个 case 汇总：任一轮硬失败则全 case 不通过；后续修复保留前轮失败，不将一次评测重试增记一个新 case。

四类互斥判定由渲染器实现，字段和精确优先级以[渲染器](../scripts/render_report.py)的校验函数及 `demo` 生成的合成 JSON 为准。思考不可见本身不判失败，若完整调用轨迹及最终对账能充分判断顺畅性，可通过并明确思考缺失；顺畅性的证据不足则 unknown。

所有计数和指标使用明确单位：

- 按唯一 tool_call_id 计调用，start/end 两事件算一次；相同参数的新调用 ID 是另一次，不按请求内容去重。
- 运行层失败与业务 error 各自统计；回包 `status=success` 嵌套 NOT_SUPPORTED 等仍是业务不可用。失败返回的空数组不是完整空集。
- 重试须有同一操作身份/修正上下文，不能把两项相同类型任务误算为重试；按调用、批次、case分别表述。
- 使用平台权威 usage 去重，不能叠加每轮累计快照；缺失保留 null，不转零。输入/输出 tokens 为多请求累计时写清，不等于独有上下文量。
- 工具 latency 累加不是并行关键路径；思考事件至下个调用的间隔包含模型输出和请求组装，不称纯思考时长；不直接用总耗时减工具累加得模型耗时。
- 改进收益未经重跑比较时只写预期和验收方式，不编造节省比例或提升通过率。
