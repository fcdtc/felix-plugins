# go-service-structure

面向 Go 微服务目录结构设计与治理。

默认约束如下：
- 保留 `kitex_gen/` 等 kitex 生成目录，不手改生成代码。
- 主分层以 `logic/` 和 `repo/` 为核心。
- 依赖方向必须单向：`logic -> repo`，禁止 `repo -> logic`。
- `logic` 与 `repo` 都可以依赖公共层，但公共层必须按职责命名，不能泛化成新的“大 common”。
- 同层业务目录默认不直接横向依赖；若多个业务复用同一能力，优先下沉到更低一层或公共层。

用户诉求：
$ARGUMENTS

## 你的目标

围绕当前项目或目标方案，产出一份可执行的目录结构建议，优先回答以下问题：
1. 当前目录职责是否清晰。
2. 依赖方向是否稳定，是否存在反向依赖或横向耦合。
3. 哪些内容应放入 `logic/`，哪些应下沉到 `repo/`。
4. 哪些公共层值得单独保留，例如 `entity/`、`config/`、`errno/`、`pkg/`。
5. `logic` 内部是否需要轻量缓冲分层。
6. 每个功能是否需要 `api.go`，边界应如何定义。
7. 最终给出推荐目录树、依赖规则、落地建议。

## 工作步骤

### 1. 先确认边界，再讨论目录

先用一句话明确当前方案的主骨架：

```text
handler / transport
    ↓
logic
    ↓
repo
```

然后检查这几个判断是否成立：
- `logic` 是否只承载业务逻辑、业务编排、业务规则。
- `repo` 是否只承载数据访问、缓存访问、外部 RPC/HTTP/LLM/MQ 调用。
- 是否存在业务判断写进 `repo` 的情况。
- 是否存在 `repo` 反向依赖 `logic` 的情况。

如果边界不清，先指出问题，再给目录建议；不要直接堆目录名。

---

### 2. 用职责来划分公共层

只有在职责稳定时，才建议单独建目录。默认按下面标准判断：

#### `entity/`
适合放跨层共享的核心业务实体。

放这里的对象应满足：
- `logic` 和 `repo` 都可能引用。
- 不带 GORM/Redis/RPC/Kitex 协议细节。
- 表达的是业务概念，不是存储格式。

典型例子：
- 用户
- 会话
- 问题
- 搜索上下文
- 推荐结果
- 业务枚举

如果对象只是数据库表映射，不要放到 `entity/`。

#### `config/`
适合放配置加载逻辑、配置结构体、配置校验逻辑。

约束：
- 配置文件保留在 `conf/`。
- Go 代码里的配置定义与加载逻辑放 `config/`。
- 不把运行时业务决策塞进 `config/`。

#### `errno/` 或 `errors/`
适合放：
- 错误码
- 统一错误类型
- 错误包装与转换

#### `pkg/`
只放无业务语义的通用工具。

可以放：
- `ctxutil`
- `jsonx`
- `streamx`
- `timex`
- `retry`

不要放：
- 业务规则
- 业务配置决策
- 某个业务专属 helper
- prompt 拼装
- 按业务含义分流的逻辑

#### `model/`
谨慎使用。

如果保留 `model/`，必须先明确它只表示哪一类模型：
- DB model
- cache model
- DTO
- 业务对象

如果定义不清，优先不用单独 `model/`，改为：
- 业务对象放 `entity/`
- DB model 放 `repo/.../model.go`
- 协议对象保留在 kitex 生成代码里

---

### 3. 检查同层业务模块是否应互相引用

默认规则：
- `logic` 下不同业务目录默认不直接互相引用。
- `repo` 下不同业务目录默认也不直接互相引用。

如果确实出现同层引用，按下面顺序判断：
1. 这是不是一个公共能力，应该下沉到公共层。
2. 这是不是一个更低层能力，应该移到 `repo/` 或 `pkg/`。
3. 这是不是原本不该拆开的同一业务域。
4. 如果确实需要跨模块依赖，是否应通过 `api.go` 暴露接口，而不是直接依赖实现。

结论优先级：
- 能下沉，就下沉。
- 能抽公共，就抽公共。
- 不能下沉也不能抽公共，再保留跨模块接口依赖。

不要鼓励任意横向 import。

---

### 4. 判断 `logic` 内是否需要再分层

默认建议：需要轻量分层，但不要过度设计。

推荐的判断标准：
- 如果一个业务目录只有少量文件，先不要分层过深。
- 如果一个业务目录同时承担“入口编排、规则判断、参数校验、细节实现”，可以做轻量拆分。

推荐形态：

```text
logic/
└── xxx/
    ├── api.go
    ├── service.go
    ├── model.go
    ├── validator.go      # 可选
    └── impl/             # 可选，仅在实现细节较重时再拆
```

解释：
- `api.go`：模块对外暴露的接口与入参出参。
- `service.go`：该业务模块的主入口与核心编排。
- `model.go`：仅本业务私有的内部结构体。
- `validator.go`：参数校验规则较重时再拆。
- `impl/`：仅在细节实现过多时作为缓冲层，不要机械创建。

如果业务复杂度不高，允许只保留：
- `api.go`
- `service.go`

不要为了“分层而分层”。

---

### 5. 判断是否需要 `api.go`

原则：
- 模块边界清晰、会被别的模块依赖时，推荐有 `api.go`。
- 只是内部私有实现时，不必强制抽接口。

推荐使用场景：
- 该业务模块会被别的业务模块依赖。
- 需要稳定暴露边界。
- 需要 mock 或替换实现。
- 需要避免调用方直接 import 实现细节。

不推荐机械使用：
- 只有一个实现、且目录只在内部自用时，不要为了形式强行定义接口。
- 不要把“所有 struct 都套一层 interface”当成规范。

评价标准：
- `api.go` 应该服务于“边界清晰”，不是服务于“样板整齐”。

---

### 6. 推荐目录模板

在保留 `kitex_gen/` 和 `conf/` 的前提下，优先给出下面这版作为默认建议：

```text
project
├── main.go
├── handler.go
├── kitex_gen/                 # 保留生成代码
├── conf/                      # 配置文件目录
│
├── logic/                     # 业务逻辑层
│   ├── common/                # 仅 logic 内共享的业务能力
│   ├── picsearch/
│   │   ├── api.go
│   │   ├── service.go
│   │   ├── model.go
│   │   └── impl/
│   ├── knowledgeqa/
│   │   ├── api.go
│   │   ├── service.go
│   │   └── impl/
│   └── agent/
│       ├── api.go
│       ├── service.go
│       └── impl/
│
├── repo/                      # 数据访问与外部依赖访问层
│   ├── db/
│   ├── cache/
│   ├── rpc/
│   ├── llm/
│   ├── mq/
│   ├── common/
│   ├── picsearch/
│   ├── knowledgeqa/
│   └── agent/
│
├── entity/                    # 跨层共享业务实体
├── config/                    # 配置加载逻辑与配置结构
├── errno/                     # 错误码与错误封装
├── pkg/                       # 通用无业务语义工具
└── docs/
```

说明：
- `logic/common/` 只放业务层共享能力，不是新的总垃圾桶。
- `repo/common/` 只放 repo 内共享组件。
- `entity/` 是跨层共享的业务概念，不等于数据库 model。
- `pkg/` 必须保持克制。

---

### 7. 输出时必须明确依赖规则

最终结论里，必须显式写出依赖约束。默认写法如下：

```text
handler/transport -> logic -> repo
logic -> entity/config/errno/pkg
repo  -> entity/config/errno/pkg
repo  -X-> logic
```

并补充下面几条规则：
- `logic` 可以依赖 `repo`，`repo` 不能依赖 `logic`。
- 同层业务模块默认不互相依赖。
- 出现复用时优先下沉到更低层或抽到公共层。
- `repo` 只负责访问外部依赖，不承载业务规则。
- `kitex_gen/` 保持生成态，不手改。

---

### 8. 评审一个现有项目时，按固定模板输出

优先按这个结构输出，保持稳定：

1. **当前结构判断**
   - 当前主分层是什么。
   - 哪些目录职责清楚，哪些目录职责混乱。

2. **依赖关系判断**
   - 当前依赖是否单向。
   - 有没有 repo 反向依赖 logic。
   - 有没有同层横向耦合。

3. **公共层建议**
   - 哪些适合抽成 `entity/config/errno/pkg`。
   - 哪些不建议保留为公共层。

4. **logic 内部结构建议**
   - 是否需要轻量缓冲层。
   - 是否需要 `api.go`。

5. **推荐目录树**
   - 给出一版适合该项目的目标树。

6. **迁移建议**
   - 哪些先改。
   - 哪些暂时不动。
   - 哪些必须先定规则再迁移。

## 输出风格要求

- 先给结论，再解释原因。
- 重点讨论“职责”和“依赖方向”，不要只罗列目录名。
- 优先给可执行建议，不写空泛架构口号。
- 如果发现 `common/util/model` 之类边界模糊目录，要明确指出风险。
- 如果用户已经给出偏好，优先在其约束下优化，而不是推翻重来。

## 特别提醒

遇到下面情况时，要主动提醒：
- `repo` 里混入业务判断。
- `logic` 之间频繁横向依赖。
- `pkg` 开始承载业务语义。
- `entity` 与 DB model 混用。
- `api.go` 被机械化滥用，只有样板没有边界价值。
- 为了“分层好看”而引入过深目录。

你的任务不是追求最复杂、最教科书式的架构，而是给出一套：
- 边界稳定
- 单向依赖
- 易迁移
- 易落地
- 适合 Go 微服务长期演进

的目录结构建议。
