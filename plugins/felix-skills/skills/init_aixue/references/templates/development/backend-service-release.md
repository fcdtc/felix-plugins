# 后端构建与发布

用于首次构建镜像／制品、初始化部署链路，以及后续 `codex/dev` push 自动部署和失败恢复。平台操作先读[工具、授权与证据约定](platform-operations.md)。

本项目目标是：首次完成构建和部署初始化，绑定验证通过后由 push 触发自动部署。目前未核实 SCM／BITS／TCE 绑定，也没有已确认的构建配方；本页是实施流程，不是已部署声明或可直接执行的一键建服务命令。

## 首次实施输入

先查询仓库配置和平台已有资源，再将确实缺失的决策交给用户。所有字段须在对应阶段写入前确认，不要求文档初始化时先建资源。

| 阶段 | 必须核实的输入 |
| --- | --- |
| 服务 | 职责、owner、完整 PSM、语言／module、协议、调用方、验收与回滚边界 |
| RPC／IDL（需要时） | 唯一权威仓与文件、基线 commit、生成器版本／命令、兼容策略 |
| 首次构建 | Git 仓、SCM 仓标识、分支与精确 commit、构建类型、镜像／版本、架构、build steps、制品类型与启动入口 |
| 首次部署 | 目标环境、standard env、PSM、SCM 制品、首次创建／升级模式、地域／zone／资源池／IDC、配额、规格、实例数、租期 |
| 自动链路 | DevTask／Change Card、触发规则、source／target branch、project／main pipeline、目标部署资源、业务门禁 |
| 验收与恢复 | 实例及注册检查、获准接口／业务 case、日志与指标、回滚制品、允许的资源写入范围 |

上述服务及平台输入当前均待确认；地域、IDL 归属和协议也不沿用历史项目默认值。仓库名不能推导完整 PSM、module 或 SCM 标识。

## 首次构建与链路初始化

1. **固定服务与代码输入。** 确认服务方案和权威契约；按[开发环境](environment.md)完成骨架、生成、实现及本地检查。构建输入不依赖相邻 checkout。完成标准：能列出本次构建源及精确 commit，本地检查结果与缺口明确。
2. **识别“打镜像”的实际方式。** 查询 SCM 现有配置与团队构建规范，区分构建环境镜像、SCM 服务制品和服务容器镜像。本项目尚未选择制品类型，不默认使用 Docker，也不把构建环境镜像当作服务发布镜像。完成标准：镜像／制品来源、架构、build steps 和启动入口均有依据。
3. **完成首次构建。** 核对自动任务是否已存在；按授权配置或复用构建入口，再跟进唯一构建任务。检查失败步骤及日志。完成标准：目标 commit、SCM 版本、构建成功终态和实际 artifact 一一对应；需要容器镜像时记录平台返回的镜像标识／digest。
4. **完成首次部署。** 核对部署输入和可用配额，能力支持时先 pre-check；提交后回读原工单及实例。完成标准：工单终态成功，实际实例使用目标制品并 Ready／Running，服务注册符合预期。结果不明或部分创建先回读恢复，不重复新建。
5. **绑定并验证自动触发。** 核实 `codex/dev` 触发规则、负责本服务的 project pipeline、SCM 和目标部署资源，以及 main pipeline 的门禁。用获准的实际推送验证链路，而不仅检查配置存在。完成标准：一次推送可以定位唯一自动 run，并通过下节的制品、部署与业务验收。
6. **交付初始化结果。** 将已确认的稳定入口维护到本仓配置或文档，将任务 ID、版本和验收证据记录到实施工单。未完成绑定或业务验收时分别报告，不能宣布“后续 push 即可部署”。

## codex/dev 自动部署闭环

仅在目标分支已绑定自动构建／部署时使用。提交与推送仍需明确要求，见[Git 约定](environment.md#git-与-worktree)。

1. **Push 前核对绑定。** 回读 DevTask 的分支、Change Card、stage、project／main pipeline 和最近 run，确认目标环境与本次精确 commit。完成标准：任务归属和触发影响明确，无同目标运行链路被遗漏。
2. **Push 后跟进原 run。** 定位本次 commit 自动产生的 run；未出现时先刷新任务与流水线，排除延迟创建或已有任务。完成标准：只跟进一条目标构建／部署链；不并行启动手工 SCM 构建或部署。
3. **验证 SCM。** 回读版本的 commit、分支、构建镜像、架构、终态和 artifact。完成标准：成功制品确实对应本次 commit，而非历史成功版本。
4. **验证部署。** 检查自动部署节点、原部署工单、目标环境／集群、实际制品和实例注册。完成标准：运行实例使用本次目标版本；重启仍绑定旧制品的实例不算升级成功。
5. **验证业务。** 跟进 main pipeline 等待卡点及其门禁，执行获准 RPC、接口测试或业务 case，并关联运行版本与日志。完成标准：本次业务断言通过；project pipeline 成功或健康检查不能代替业务验收。

构建成功、部署成功与业务通过分别给出结果。热部署按工单、制品关联和运行行为核验，不能仅因实例标识或展示版本未变化而判失败。

## 失败恢复

- 构建配置错误：回读持久配置和失败 job，确认影响范围及回滚值后修正，优先重试原节点。仓级配置可能影响其他分支和构建类型。
- 源码错误：在 `codex/dev` 修复，经明确要求提交和推送后产生新 run；失败制品不部署。
- 瞬时 job 失败：核实节点支持重试后精确重试；整条 rerun 会重复成功步骤，按任务语义决定。
- 部署失败或结果不明：先回读原工单与实态，再按授权恢复或回滚；不用重复 push 或新建部署试探状态。
- 手工构建／部署：仅在自动链路不存在、核实未触发或明确要求独立恢复时使用；仍形成同等证据并回填实施工单。

## 交付证据

记录 `Git commit → SCM 版本／artifact → 部署工单／运行版本 → 实例与注册 → 业务 case／日志`，同时记录失败任务终态、未覆盖项及回滚入口。具体证据归属见[平台操作](platform-operations.md#配置与动态证据)。

后端部署和接口验收通过后，需要接入 MIA 时继续[MIA RPC 发布链](mia-rpc-tool-host-release.md)；后端发布不代表 MIA 已发布。
