# 源码借鉴

围绕用户明确提出的方向，研究本项目与参考仓库的代码风格、架构或具体机制，以双方证据和约束判断哪些设计值得借鉴。

## 输出路由

解析 `--mode` 后，只读取对应的产物要求文件。路由在研究前确定，产物在研究完成后生成。

| 参数 | 用途 | 产物要求 |
| --- | --- | --- |
| `--mode reference` | 生成供后续 agent 按需读取的技术参考文档 | [技术参考文档](references/technical-reference.md) |
| `--mode discuss` | 纯探讨，以图解辅助用户理解设计和取舍 | [图解探讨](references/discussion.md) |

未传参数时，用户明确要求“纯探讨”或“技术参考文档”的措辞分别等价于上述模式；既无参数也无明确模式时，默认 `reference`，保持原有行为。参数与文字要求冲突、或参数值不受支持时，先请用户澄清。一个调用只生成所选模式的产物，不附带另一种产物。

仅在用户手动调用时执行。写入范围由所选产物要求限定；研究阶段只读，不修改项目代码、Spec、ADR、`GLOSSARY.md`、代理指令或其他技能。

## 1. 确定问题与材料

- 获取参考仓库的位置及用户明确提出的借鉴方向；方向可以是“模块划分”“错误处理风格”“插件扩展机制”等设计问题。用户只指定仓库时，先询问希望借鉴的方向。
- 默认当前工作目录为本项目，将方向整理成双方共同回答的研究问题，明确期望用途。已有材料能回答的事实自行查找；参考仓库或影响分析的必要目标约束缺失时，向用户询问。
- 为双方分别确定相关代码、约定和文档入口；本项目尚无代码时，使用用户提供的目标和约束。一个主题可引用多个指定仓库。
- 按所选产物要求确定输出路径。

完成条件：模式和路径已确定，参考源码可读取，研究问题与本项目上下文明确。源码无法访问时，说明缺失材料，不以猜测替代研究。

## 2. 双库探索

分别建立本项目与参考仓库在同一方向上的设计理解。有 subagent 工具时，在同一消息中并行派出两个只读探索 agent，各负责一个仓库；否则依次直接探索。每份任务包含仓库位置、共同研究问题、该仓库的相关入口和下述证据要求。

探索 agent 通过读取文件复用 [`how/SKILL.md`](../pstack/how/SKILL.md) 及其链接的完整流程，解释各自仓库在该方向上的职责、运行流程、模块边界与取舍。这是内容引用，而非 Skill 工具调用；`how` 保持 `disable-model-invocation: true`。派发前将相对链接解析为当前安装位置下的实际 `SKILL.md` 路径，写入任务，使 agent 能继续解析入口中的相对链接。探索结果返回主线程，由主线程比较并生成所选产物。

先查看各自仓库的相关目录、入口和代码分布，再分配阅读范围：范围集中时通读相关实现；分布广时按职责和实现变体抽样，并沿关键关系补读。记录实际覆盖的模块、样例与未覆盖范围，以研究问题是否得到解释决定是否继续阅读。

从入口沿调用关系、模块边界和测试追踪实现，直到能够解释行为如何产生。按主题选择检查维度：

- 风格：声明组织、命名与状态表达、横切工具、错误处理；比较重复做法，区分局部写法与项目惯例。
- 架构：职责划分、依赖方向、扩展机制及模块间协作。

为每个候选借鉴点选择代表性实现，说明样例选择理由、阅读入口、相关调用方或测试。存在其他做法时，比较使用场景和约束；出现频率仅作为惯例的证据，迁移建议由本项目需求决定。

收集最小充分证据：仓库标识、仓库内相对路径、实际读取的行号范围和关键符号名。跨模块设计须覆盖模块间关系；用例和测试可说明行为与边界。多个仓库的相同路径必须能够区分。

区分源码可验证的事实、设计理由的推断和未知部分。注释或文档明确说明的理由可以引用；仅凭实现推测的动机标为推断。参考仓库按静态源码处理，定位使用本次读取的路径、行号与符号。

每个探索 agent 返回：逐问题的设计解释、职责与运行流程、边界与约束、代表性样例及源码证据、实际阅读范围和缺口。本项目尚无实现时，返回有来源的目标与约束，明确哪些设计仍未确定。

完成条件：双方探索均已返回；每个研究问题在双方都有支撑结论的证据，或明确记下搜索范围与缺口；候选借鉴点有代表性样例；指针已核对实际源码，双方阅读范围已记录。主线程对影响比较的矛盾或缺口定向补读后，再进入提炼。

## 3. 提炼借鉴方式

逐条对照双方如何解决同一问题，以及各自的目标和约束，提炼可迁移的原则、机制或风格与必须调整的部分。说明收益、代价和不适用条件；本项目尚无实现时，建议落到预期职责与行为上。

检查样例中可见的缺陷、偶然写法和历史包袱，区分值得借鉴的结构与应避开的细节，附上证据或推断标记。不同做法按上下文并列解释；缺少必要约束、无法判断适用性时，才向用户询问。

建议应能回答“写到哪一环节，为什么看这段源码，以及看完如何指导本项目”。采用参考仓库的依赖、技术栈或目录结构，需要给出与目标问题的关联理由。证据不足时记录缺口。

完成条件：每个建议均关联本项目问题、源码证据和适用条件，事实与推断可以分辨。

## 4. 生成所选产物

执行路由选中的产物要求，并完成其中的检查。最后返回模式、产物路径、覆盖的问题和未解决的缺口。
