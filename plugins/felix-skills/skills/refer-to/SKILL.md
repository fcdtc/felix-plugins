# 源码借鉴指南

把指定仓库的设计思路转化为当前项目可使用的指导文档，覆盖代码风格、架构或具体机制。以目标项目的问题组织研究，以源码作为证据，以适用条件连接两者。

仅在用户手动调用时执行。产物独立于其他技能，由用户按需引用；写入范围限于目标项目的 `docs/references/<主题>.md`。不修改项目代码、Spec、ADR、`GLOSSARY.md`、代理指令或其他技能。

## 1. 确定问题与材料

- 获取参考仓库的位置及用户明确提出的借鉴方向；方向可以是“模块划分”“错误处理风格”“插件扩展机制”等设计问题。用户只指定仓库时，先询问希望借鉴的方向。
- 默认当前工作目录为本项目，将用户的方向整理成双方共同回答的研究问题，明确期望用途。已有材料能回答的事实自行查找；参考仓库或影响分析的必要目标约束缺失时，向用户询问。
- 为本项目与参考仓库分别确定与方向相关的代码、约定和文档入口；本项目尚无代码时，使用用户提供的目标和约束。
- 确定 `docs/references/` 下的主题文件：优先复用已有同主题文档，新文件使用简短、明确的主题名。一个主题可引用多个指定仓库。

完成条件：参考源码可读取，研究问题明确，目标上下文与输出路径已确定。源码无法访问时，说明缺失材料，不以猜测替代研究。

## 2. 双库探索

分别建立本项目与参考仓库在同一借鉴方向上的设计理解。有 subagent 工具时，在同一消息中并行派出两个只读探索 agent，各负责一个仓库；否则依次直接探索。每份任务包含仓库位置、共同研究问题、该仓库的相关入口和下述证据要求。

探索 agent 通过读取文件复用 [`how/SKILL.md`](../pstack/how/SKILL.md) 及其链接的完整流程，解释各自仓库在该方向上的职责、运行流程、模块边界与取舍。这是内容引用，而非 Skill 工具调用；`how` 保持 `disable-model-invocation: true`。派发前将相对链接解析为当前安装位置下的实际 `SKILL.md` 路径，写入任务，使 agent 能继续解析入口中的相对链接。探索结果返回主线程，主线程负责比较和写入指南。

先查看各自仓库与主题相关的目录、入口和代码分布，再分配阅读范围：范围集中时通读相关实现；分布广时按职责和实现变体抽样，并沿关键关系补读。记录实际覆盖的模块、样例与未覆盖范围，以研究问题是否得到解释决定是否继续阅读。

从相关入口沿调用关系、模块边界和测试追踪实现，直到能够解释行为如何产生。按主题选择检查维度：

- 风格：声明组织、命名与状态表达、横切工具、错误处理；比较相关实现中的重复做法，区分局部写法与项目惯例。
- 架构：职责划分、依赖方向、扩展机制及模块间协作。

对每个候选指导条目选择一个代表性实现，说明它为何适合作为阅读样例，标明阅读入口以及帮助理解它的调用方或测试。存在其他做法时，比较各自的使用场景和约束；出现频率仅作为惯例的证据，迁移建议由目标项目的需求决定。

为每个候选指导条目收集最小充分证据：仓库标识、仓库内相对路径、实际读取的行号范围和关键符号名。跨模块设计需要覆盖相关模块之间的关系；用例和测试可补充说明行为与边界。多个仓库的相同路径必须能够区分。

区分源码可直接验证的事实、对设计理由的推断和仍未知的部分。注释或文档明确说明的理由可以引用；仅凭实现推测的动机标为推断。参考仓库按静态源码处理，定位使用本次读取的路径、行号与符号。

每个探索 agent 返回：逐问题的设计解释、职责与运行流程、边界与约束、代表性样例及源码证据、实际阅读范围和未解决的缺口。本项目尚无实现时，返回有来源的目标与约束，明确哪些设计仍未确定。

完成条件：双方探索均已返回；每个研究问题在两个仓库中都有足以支撑结论的证据，或明确记下未找到证据的范围与缺口；每个候选条目均有代表性样例；每个指针均已核对实际源码，双方实际阅读范围已记录。主线程对影响比较的矛盾或缺口定向补读后，再进入提炼。

## 3. 提炼借鉴方式

逐条对照双方探索结果，比较本项目的现有设计与参考设计如何解决同一问题，以及各自的目标和约束，提炼可迁移的原则、机制或风格，以及必须调整的部分。说明收益、代价和不适用条件；目标项目尚无实现时，建议落到预期职责与行为上。

检查代表性样例中可见的缺陷、偶然写法和历史包袱，指出值得借鉴的结构与需要避开的细节，并为判断附上证据或推断标记。不同做法按各自上下文并列解释；只有缺少目标项目的必要约束、无法判断适用性时，才向用户询问。

建议应能回答“写到哪一环节，为什么看这段源码，以及看完如何指导本项目”。采用参考仓库的依赖、技术栈或目录结构，都需要给出与目标问题的关联理由。若证据不足以支持迁移，记录缺口，而不是硬凑借鉴结论。

完成条件：每个建议均关联目标问题、源码证据和适用条件，事实与推断可以分辨。

## 4. 写入指南

文档面向后续按需读取的 agent，使用以下结构；条目标题采用明确的设计问题，便于按章节引用：

```markdown
# <主题>借鉴指南

## 范围与上下文
本项目与参考仓库的标识、可访问位置、各自目标及约束；共同研究问题；双方实际阅读的模块与样例、抽样方式及未覆盖范围。

## 参考索引
用表格列出：何时参考 | 对应指导条目的章节链接。

## <具体设计问题>
### 何时参考
编写或设计到什么环节、遇到什么问题时读取本条。
### 设计思路与源码指针
参考实现的机制或风格；代表性样例及选择理由、阅读入口和相关调用方或测试；仓库、相对路径、行号范围、关键符号及其证明的事实。
### 设计理由与取舍
为什么这样设计、收益与代价；发现不同做法时说明各自场景与约束；区分有来源的理由、推断和未知。
### 对本项目的指导
本项目当前如何处理同一问题及其证据（尚无实现时列出目标与约束）；与参考设计的差异；适用条件、建议借鉴的部分、需要调整的部分及不适用边界；发现样例缺陷或历史包袱时，指出应避开的细节及依据。

## 未解决的问题
证据缺口、尚缺的目标约束及因此无法确定的建议；没有则省略。
```

按实际条目重复“具体设计问题”章节。保持文档自足：后续使用者只凭本文件就能知道何时参考、去哪里看和如何判断是否适用；源码保留在参考仓库，指南只摘录解释设计所必需的片段。

同主题再次执行时，先读原文，保留仍成立的内容，合并新发现并修正旧结论，尽量保留已有章节锚点。保留用户补充的上下文；遇到无法确认的矛盾，在文档中明确列出。不同主题分别建文件。

完成条件：指南已写入指定路径；索引链接有效；所有源码路径、行号和符号可定位；每个指导条目满足上述结构；更新时原有相关内容已逐项处理。最后返回文档路径、覆盖的问题和仍未解决的缺口。
