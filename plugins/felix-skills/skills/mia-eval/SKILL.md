# MIA Agent 执行审计

使用既有运行证据，回答：**这个固定版本的 Agent 要做什么；它有没有正确使用工具、处理完本轮流程，以及任务没处理完就提前结束。** 只读平台，不重跑评测、不修改 Agent/Skill/Tool、不执行业务写入。

默认评 Agent 的行为，不验 Tool 后端是否真实保存、排程或发送。**Tool 是 Mock 不影响通过判定**；按 Agent 当轮可见契约检查请求、回包处理及后续动作。真实服务落盘、送达及 Mock 实现核验不属于本技能默认范围。完整判定见[审计标准](references/audit-rubric.md)。

用户显式调用即选择逐 case 独立子代理分析。并发数未指定时默认 3；用户指定时按指定并发数执行，记为本轮并发数 N（正整数）。取得总量后说明样本数、本轮并发数及分析消耗模型 tokens；覆盖全部选定 case，不静默抽样。Agent 工具可用时直接调度；仅有 Workflow 工具时先加载宿主编排规范，实现同一有界队列。没有子代理能力时说明阻塞，不用主线程批读冒充独立审计。

## 报告表达

所有面向用户的结论、问题标题、层级、检查说明和 case 描述，都像一个人跟另一个人说明发生了什么：用直白、简短、连贯的中文，让用户不用懂评测方法也能读懂。

- **先说具体行为。** 写清本来要做什么、实际做了什么、哪里没做对，以及用户因此拿到了什么或缺了什么。标题直接说问题，例如“查到了两个任务，只处理了第一个就结束”。
- **专业术语仅限待评测 Agent 设计中已出现的词。** 工具名和业务名按设计原文保留，必要时用日常用语解释；严禁引入额外术语或创造概念，不能把审计标准中的内部分类名当成用户已知的词。
- **层级说清出问题的环节。** 用设计里已有的 Agent、Skill、Tool 或具体工具名，必要时补一句它负责什么；尚未定位时写“暂时无法确认问题出在哪个环节”，不强猜原因。
- **具体 case 要有经过。** 从该 case 的记录写出任务、关键动作、结果或遗漏，保留必要数量、状态和顺序；链接只是入口，不能代替解释。辅助例子明确标为“例如”，与实际观察分开。
- **不确定就直说缺什么。** 例如“没有拿到后续调用记录，暂时无法确认第二个任务是否处理完”，不补写事实。

**汇总只讲问题。** “问题汇总”按 P0/P1/P2 严重程度排列，每条只列层级、问题及具体 case；不写修改建议或验证办法。结论和最终交付说明同样围绕已发生的问题。

## 1. 定位目标与审计问题

先从用户提供的执行任务 URL 定位任务，再补齐固定目标；不要求用户分别提供两组定位信息：

- **执行任务 URL**：解析 task_id、space_id，先用官方 `evaluation task get` 回读任务。优先从任务的 agent_eval_config.agent_id、agent_eval_config.version 和 motif_id 取得固定 Agent，再用 `agent get` 核验；能唯一定位时直接继续，不重复索要 Agent 设计链接、ID 或版本。数据集 URL 没有轨迹，先用官方 CLI 查关联任务；无法唯一对应时请用户选择。
- **固定 Agent 版本**：用户另给设计页 URL 或 agent_id、motif_id、发布版本时复用并与任务核对；关联信息缺失、冲突或无法唯一定位时才请求最小补充。agent_id 能权威回读所属 motif/发布版本时自行补齐；仅有浮动草稿或“最新版”时请求固定目标。精确草稿 agent_id+revision 仅适用于评测运行同一草稿且有完整快照。

默认关注流程、工具使用和结束时机。用户已明确关注点时直接采用；先读目标版本能解决的事实不交给用户猜。只有审计目的或成功标准仍有两种会改变判定的解释时，**在分派 case 前调用 `felix-skills:grilling`**，集中澄清关注点、什么算处理完成以及受阻如何计分；技能不可用则直接问同样的必要问题。已清楚的需求不机械 grilling，也不为平台身份信息启动 grilling。

默认仅审计抓取截止时**待评价（ToEvaluate）**的 case，覆盖这些选定数据项的完整轮次；已评价、运行失败和运行中项默认排除，用户明确要求时才扩大范围。一个数据项为一个 case，重试不增加分母；筛选及数量核对见[取证规则](references/acquisition.md)。默认落盘到**执行本 skill 的目标项目**根目录的 `.eval/mia-eval-<时间戳>-<唯一后缀>/`，不是本 skill 源码仓库或插件安装目录的 `.eval/`；每次新建独立私有目录，用户指定输出目录时优先采用。路径定位及 Git 忽略规则见[目录与分工](references/dispatch.md)。冻结抓取截止、版本、范围和排序；后续运行不混入分母。

**完成条件：** 固定目标、任务、空间/环境、范围、私有路径和审计关注点明确。

## 2. 回读版本，先理解设计

加载官方 `miacli` 的 evaluation、agent-design subskill，遵守项目操作规范，按当前 `--help` 与[取证规则](references/acquisition.md)读取任务、完整分页清单和必要导出。

1. 回读**指定版本**的完整 System、User 模板、附加 Skill/Tool Prompt、输入输出 Schema、模型配置和固定 Skill/reference。共享基线只取一次，保存原文件与 SHA-256。草稿/最新文档不能覆盖历史基线。
2. 写 `baseline/design-summary.json`：Agent 的主要目的、场景入口、适用职责及顺序、必需工具与使用条件、逐项结果和合法退出条件。规则附来源位置。它是设计的摘要，不是主线程对某 case 的预判。
3. 在 manifest 的 `audit_scope` 写明 `profile=agent_flow`、关注点、Agent目的、流程收尾标准及排除项。排除项明确包含 Tool Mock/真实持久化/实际送达。每个 case 的必查项为 identity、design、tool_usage、execution、completion_gate、smoothness。
4. 检查输入、实际Prompt、原输出、改后输出、评分评论、调用、可见思考、版本、终态与耗时覆盖；URL优先、CSV可选，只因实际缺字段请求最小补充。运行快照回答“当时看到了什么”，固定版本回答“要求什么”，差异单独记录。
5. 按[目录与分工](references/dispatch.md)生成每 case 资料包及稳定映射；ID 全部字符串无损保存。manifest 只包含冻结选定范围；选入后发生取证/分析失败或缺证仍保留占位，不删分母。范围外的平台失败、运行中及已评价项不混入默认分母。

**完成条件：** 有可引用的版本职责与收尾标准，不只拿到配置；清单全量或显著标记部分；每个 case 的版本关联与证据缺口明确。

## 3. 逐 case 独立审计

读取[审计标准](references/audit-rubric.md)、[分工模板](references/dispatch.md)及[渲染器](scripts/render_report.py)校验/demo。每 case 启动全新子代理，返修复用原代理。交付自己的完整输入、共享设计摘要和基线，不附其他 case 结论或主线程预判。

每个 worker：

1. 按需用官方 CLI 补齐本 case history/debug，先索引大日志再按检查范围读取，避免反复展开整包。
2. 按本轮场景列出全部应处理对象与阶段，逐项对照规则、实际工具请求、回包及后续行为。
3. 专项检查正确工具与参数、分页/对象关联、成功和失败回包处理、独立项继续，以及**最终 response 前是否已处理完全部职责**。区分阶段进度文本与真正结束。
4. 用可见思考解释误读、返工和决策反复；合理验算不算挣扎，缺失思考不编造。
5. 写 `reports/<case_key>.json`，用固定渲染器生成 `site/cases/<case_key>.html`；回传三轴结论、重要发现/缺口及路径。原始日志留私有目录。

主线程按本轮并发数 N 持续补位，不等待整批完成；运行限制的处理见[调度规则](references/dispatch.md)。不重读 worker 全量日志。失败有限重试一次；仍失败保留证据不足占位，不删分母。

**完成条件：** 每个选定 case 都有独立结果或失败占位；每个应处理项有结果或合法退出依据；提前结束检查有最终事件与未完成项证据；Mock 不形成 Agent 失败理由。

## 4. 核验、归并、统计

主线程核验身份、覆盖、检查与结论一致性；P0/P1 定点读引用，必要时退回原 worker。缺陷归最早有证据的失效层，工具请求失真未定位时不直接归罪模型。平台实现背景放 `limitations` 或 `scope=platform_context` 的发现，不进入 Agent 通过率。

把出错环节和具体行为相同的问题归并到 `synthesis.json` 的 `issues`，按“报告表达”写问题及每个受影响 case 的经过。只纳入本次 Agent 流程、工具使用和收尾范围的问题；假设或证据缺口明确说明，不能写成已确认事实。每条的 `examples` 覆盖全部受影响 case，同一 case 只列一次；数量由脚本计算，不用调用失败次数增加案例数。

固定渲染器重算：

- **顺畅通过率 = 遵循设计、处理完流程且无执行挣扎的 case / 全部选定 case**。
- 四类：顺畅通过、恢复/挣扎、不通过、证据不足；互斥且总数等于分母。
- 合法静默/保持/受阻可完成流程：要满足本版本退出规则，继续其他独立项并如实交接。仍有可做任务就最终结束、用未确认回包认领成功、跳过硬门槛均不通过。
- 正确处理不可用回包不因业务错误计数自动降级；恢复返工不算顺畅；没有证据证明流程收尾则不补通过。
- 设计遵循、流程完成、工具使用、结束时机分别展示，不因另一轴失败抹去本轴已有通过证据。

执行 `summary` 生成 `site/index.html`，校验数据与全部详情互链。浏览器可用时检查一次合成/脱敏页的桌面与手机布局。最终比率由脚本产生，不手填。

**完成条件：** 统计可复算、详情可打开、每个问题和具体 case 的描述均可追到记录；汇总符合“报告表达”，没有修改建议或验证办法；审计口径可见，没有把 Mock 或合法受阻混成 Agent 失败。

## 5. 交付

给出实际汇总HTML绝对路径、逐case目录、样本数、顺畅通过率、主要问题及范围边界。按“报告表达”解释未通过的行为和具体 case，也保留通过环节。固定模板无需联网。

默认仅本地私有保存。真实身份、签名链接、凭据与整段思考不进入HTML。明确要求在线分享时先确认可发布的脱敏内容，再按宿主能力发布；本地路径不是在线URL。

**完成条件：** 用户拿到可浏览文件和统计，知道评的是Agent流程而非后端真假；说明未修改平台、重跑或外部发布。历史报告不自动改标，本次技能修改也不冒充重新审计。
