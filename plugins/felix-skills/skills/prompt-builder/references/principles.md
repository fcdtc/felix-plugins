## 1. 结果导向 vs 过程堆砌

现代模型（尤其 GPT-5.x）在"定义结果、留出路径"时表现最好。旧式 prompt 喜欢规定每一步，因为早期模型需要更多脚手架才能保持正轨。但现在这会加噪音、收窄搜索空间、让回答变得机械。

**好的写法（描述终点）**：

```
端到端解决客户的问题。

成功意味着：
- 资格判定基于可用的政策和账户数据
- 任何允许的动作在回复前已完成
- 最终答案包含 completed_actions、customer_message、blockers
- 如果证据缺失，询问最小的缺失字段
```

**避免的写法（规定每一步）**：

```
先检查 A，再检查 B，然后比较每个字段，然后想清楚所有可能的例外，
然后决定调用哪个工具，然后调用工具，然后向用户解释整个过程。
```

## 2. 显式停止条件

这是 Agent prompt 最易遗漏的部分。没有停止条件，agent 要么过早停，要么无限循环。

**检索预算（适用于研究/RAG 类）**：

```
对于普通问答，先用一次宽泛搜索（用短而有区分度的关键词）。如果顶部结果已包含足够的可引用支撑来回答核心请求，就基于这些结果回答，不要重复搜索。

只在以下情况再做一次检索：
- 顶部结果没有回答核心问题。
- 缺少必需的事实、参数、所有者、日期、ID 或来源。
- 用户要求详尽覆盖、对比或完整列表。
- 必须读取某个特定文档、URL、邮件、记录或代码产物。
- 否则答案会包含一个重要且无支撑的事实性主张。

不要为了改善措辞、加例子、引用非必要细节，或支撑可以安全泛化的措辞而重复搜索。
```

**通用停止规则模板**：

```
用最少的、足以正确回答的证据，精确引用，然后停止。
```

## 3. 慎用绝对词

文档反复强调：旧 prompt 用 `ALWAYS`/`NEVER`/`must`/`only` 来控制行为。这些词只该用于**真正的硬性不变量**——安全规则、必填输出字段、绝不该发生的动作。对于判断题（何时搜索、何时提问、何时用工具、何时继续迭代），用决策规则替代。

**绝对词的正确用法**（真不变量）：

```
- 涉及付款、删除、写生产环境的动作，必须先获得用户明确许可。
- 绝不编造引用、URL 或数据。
```

**避免的用法**（判断题不该用绝对词）：

```
- 必须总是先搜索再回答。  ← 太死，简单问题不需要搜索
- 只能调用工具一次。      ← 太死，复杂任务可能需要多次
```

## 4. 工具规则要具体（仅工具型 agent）

**仅当 agent 真的会调用工具/函数时**才写这一节。每个工具要说明：做什么、何时用、何时不用、参数从哪来。非工具型 agent（纯对话/写作/分析）凭空加工具章节反而引入幻觉和乱调用的风险。

**好的工具描述示例**：

```
工具：create_reservation
作用：为客人创建餐厅预订。当用户要求用给定姓名和时间订桌时使用。

- 当用户要求预订、订桌或安排时，调用 create_reservation。
- 不要猜预订时间或姓名——缺哪个就问哪个。
- 用户没给姓名时，问："预订用哪个名字？"
- 用户没给日期/时间时，问："您想预订哪天什么时间？"
- 调用工具后，自然地确认："您 [姓名] 在 [日期/时间] 的预订已确认。"
```

注意：描述简洁（1-2 句说"做什么 + 何时用"）；详细的"何时用"规则放在 prompt 主体，而非堆进工具定义。

## 5. 锁死输出契约

模型对输出格式高度可引导。当结构能提升可读性或产品需要稳定产物时，明确锁定。

**结构化输出契约**：

```
- 只输出要求的格式。
- 不要加散文或 markdown 代码围栏，除非明确要求。
- 验证括号和花括号是否配平。
- 不要发明表格或字段。
- 如果必需的 schema 信息缺失，询问用户或返回一个明确的错误对象。
```

**长度与受众指引**：

```
面向资深业务受众撰写。答案控制在 400 字以内。用短段落，只在能提升可扫描性时用列表。结论优先，然后是推理，然后是注意事项。
```

## 6. 定义缺失信息的行为

不定义就会导致幻觉。明确三种行为之一：(a) 检索、(b) 提问、(c) 标注假设后推进。

**不确定性处理**：

```
- 如果问题模糊或欠定义，明确指出，并：提出 1-3 个精确的澄清问题，或给出 2-3 种合理解释并标注假设。
- 当外部事实可能近期有变（价格、发布、政策）且无工具可用时：用概括性语言回答，并说明细节可能已变。
- 不确定时，绝不编造确切数字、行号或外部引用。
- 不确定时，优先用"基于提供的上下文……"而非绝对主张。
```

## 7. 止损：定义"何时停下来问用户"

最该写明白、却最常被省略的，是"出错时该不该惊动人"。规则只有一句：**错误越不可逆、越影响外部、代价越高，越要停下来问用户；反之可逆、纯本地、低代价的，自行重试或回退，不打扰用户。**

**必须停下来问用户的错误**（不可逆 / 影响外部 / 花钱）：写脏数据、删改文件或记录、发消息或邮件、触发付款或下单、调用付费 API、改生产环境、批量操作、用户未明确授权的动作。这类错误一旦继续，损失会放大或无法回收。

**自行重试或回退、不惊动用户的错误**（可逆 / 本地 / 低代价）：格式不符、单次检索或解析失败、临时超时、本地计算出错。重试一两次或换方法通常就好。

**好的写法**：

```
- 遇到删除、发送、付款等不可逆动作前，先和用户确认——一旦执行无法撤销，错误执行的代价远高于多花几秒确认。
- 调用付费 API 或批量操作前，先报告预计用量并等待确认。
- 遇到格式不符、临时解析失败等可逆错误，最多重试 2 次后换方法回退，无需询问用户。
```

**避免**：只写"出错就处理"——这等于没写，模型仍会自行决定是硬做还是停。

## 8. 格式服务理解

让格式服务于理解，而非让结构比内容更重。

**对话式格式默认**：

```
让格式服务理解。正常对话、解释、报告、文档、技术写作默认用平实的段落。保持呈现干净易读，不要让结构显得比内容更重。

谨慎使用标题、加粗、列表和编号列表。仅在用户要求、答案需要清晰的对比/排序、或信息作为散文更难扫描时才用。否则优先短段落和自然过渡。

尊重用户的格式偏好。如果他们要求简洁答案、最小格式、无列表、无标题或特定结构，除非有强理由，否则遵循。
```

## 9. 解释 why 而非堆命令

现代 LLM 聪明，有良好的心智理论。给理由比堆命令更有效。如果发现自己在大写 `ALWAYS`，这是黄牌——尝试重构并解释为什么。

**避免**：

```
你必须总是先验证再执行。
```

**更好**：

```
回答前先核对数字的来源——因为用户会据此做决策，一个错误的数字比晚几秒回答代价高得多。
```

（关于"不可逆动作要先确认"的完整规则，见 [第 7 条 止损](#7-止损定义何时停下来问用户)——那是它的权威定义处。）

## 10. 人格与协作方式分离

对面向客户的 agent，把"人格"和"协作方式"分开，且都保持简短：

- **人格**控制 agent 听起来如何：语气、温度、直接程度、正式度、共情。
- **协作方式**控制 agent 如何工作：何时提问、何时假设、多主动、何时检查工作、如何处理不确定性。

两者都不该取代清晰的目标、成功标准、工具规则或停止条件。

**简洁人格示例**：

```
# 人格
你是一个能干的协作者：平易、稳健、直接。假设用户是有能力且善意的，用耐心、尊重和实际的帮助来回应。
请求已经清楚到可以尝试时，优先推进而非停下来澄清。用上下文和合理假设向前走。只有当缺失信息会实质改变答案或带来有意义的风险时才问澄清，且问题要窄。
保持简洁但不至于生硬。给够让用户理解和信任答案的上下文，然后停。
```

## 11. 矛盾指令的危害

GPT-5.x 对指令遵循极其敏感。**矛盾的指令会让模型耗费推理 token 试图调和矛盾**，而非随机选一个——这会导致行为错乱。这是文档中反复出现的"对抗性示例"教训。

**检查清单**（交付前必过）：

- 通读全文，找"既要简洁又要详尽""既要先验证又要立即执行"这类张力。
- 明确指令优先级：安全/诚实/隐私约束 > 用户最新指令 > 默认风格。
- 更新指令时，明确说"新指令覆盖旧的风格偏好，但安全约束不让步"。

## 12. 推理强度作为最后一公里旋钮

`reasoning_effort`（none/low/medium/high/xhigh）不是提升质量的首要手段。先把 prompt 写好——输出契约、验证循环、工具规则——再考虑调推理强度。

**经验法则**：

- `none`：快速、成本敏感、无需思考的任务（字段提取、简单分类、支持分流）。
- `low`：延迟敏感但需要一点点思考来提升准确率。
- `medium`：大多数需要推理的任务的良好默认。
- `high`/`xhigh`：长程 agent、多文档综合、策略写作；只在 medium + 好提示仍不够时再升。

注意：在调高推理强度前，先加完整性契约、验证循环、工具持久性规则。提示工程通常比调旋钮更划算。
