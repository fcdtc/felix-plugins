# Agent / 工具调用场景专项策略

当用户的 prompt 是驱动一个 Agent（多步推理、调用工具、长流程执行）时，除通用原则外，重点应用以下策略。这些来自 OpenAI 文档中针对 GPT-5.x 系列的 agent 最佳实践，但原则跨模型通用。

## 1. 工具持久性（Tool Persistence）

**问题**：agent 常见失败模式是"看起来终点很明显，就跳过了必要的前置步骤"。

**对策**：当正确性依赖工具调用时，明确要求持续调用，直到任务真正完成 + 验证通过：

```
- 只要工具能实质提升正确性、完整性或事实准确性，就用工具。
- 不要因为"看起来答案已经够了"就提前停下，当另一个工具调用很可能进一步提升质量时。
- 持续调用工具，直到：(1) 任务完成，且 (2) 验证通过。
- 如果工具返回空或部分结果，换一种策略重试。
```

## 2. 依赖检查（Dependency Checks）

**问题**：agent 跳过前置查找，直接做最终动作。

**对策**：明确要求先检查前置依赖：

```
- 在执行一个动作前，先判断是否需要前置的发现/查找/检索步骤。
- 不要因为"最终动作看起来很明显"就跳过前置步骤。
- 如果任务依赖某个前置步骤的输出，先解决那个依赖。
```

## 3. 并行 vs 串行工具调用

**原则**：独立的检索/查找步骤并行（省时间）；有依赖、有歧义、或动作不可逆时串行。

```
- 多个独立的检索/查找步骤，优先并行调用以减少耗时。
- 不要并行化有前置依赖、或前一个结果决定下一步动作的步骤。
- 并行检索后，先暂停综合结果，再决定后续调用。
- 选择性并行：并行独立的信息收集，不做投机性/冗余的工具调用。
```

## 4. 完整性契约（Completeness Contract）

**问题**：agent 跑了一半就交差，漏掉批次里的项目，或把空检索当成"无结果"。

**对策**：明确定义"完成"和"未完成"：

```
- 在所有请求的条目都已覆盖或显式标记 [blocked] 之前，视为未完成。
- 维护一份内部清单，跟踪必要交付物。
- 对于列表/批次/分页结果：确定预期范围、跟踪已处理项、定稿前确认覆盖。
- 任何条目因缺数据被阻塞，标记 [blocked] 并说明具体缺什么。
```

## 5. 空结果恢复（Empty Result Recovery）

**对策**：当检索返回空/部分/可疑结果时，不要立即下"无结果"的结论：

```
如果查找返回空、部分或可疑地窄的结果：
- 不要立即断定"无结果"；
- 至少尝试 1-2 种回退策略（换措辞、放宽过滤、做前置查找、换数据源）；
- 只有尝试后才报告"无结果"，并说明试过什么。
```

## 6. 验证循环（Verification Loop）

**对策**：在交付或执行不可逆动作前，加一个轻量验证步骤：

```
定稿前：
- 检查正确性：输出是否满足每一条要求？
- 检查事实基础：事实性主张是否有上下文/工具输出支撑？
- 检查格式：输出是否符合要求的 schema/风格？
- 检查安全与不可逆性：若下一步有外部副作用，先征求许可。
```

## 7. 缺失上下文门控（Missing Context Gating）

**对策**：关键信息缺失时不要猜：

```
- 关键上下文缺失时，不要猜。
- 缺失内容可检索时，优先用合适的查找工具；不可检索时，问一个最小化的澄清问题。
- 必须推进时，显式标注假设，并选择可逆的动作。
```

## 8. 动作安全（Action Safety）—— 适用于会执行真实动作的 agent

**对策**：对主动执行动作的 agent，加一个简短的执行框架：

```
- 预检：用 1-2 行概述意图和参数。
- 执行：通过工具执行。
- 后检：确认结果，说明做了什么验证。
```

## 9. 引用与事实基础（适用于研究/RAG 类 agent）

```
- 只引用当前工作流中实际检索到的来源。
- 绝不编造引用、URL、ID 或引文区间。
- 严格使用宿主应用要求的引用格式。
- 引用附在它支撑的具体主张上，而非只堆在末尾。
```

## 10. 研究模式（Research Mode）

适用于研究、综述、综合类任务（不要强加到简单的执行任务上）：

```
- 分 3 趟做研究：
  1) 计划：列出 3-6 个要回答的子问题。
  2) 检索：搜索每个子问题，并跟踪 1-2 个二阶线索。
  3) 综合：解决矛盾，写出带引用的最终答案。
- 只有当"再搜一次也不太可能改变结论"时才停止。
```

## 11. 持续性 / 行动偏好（Persistence）

**对策**：agent 容易过早终止或把球踢回给用户：

```
- 你是一个自主的高级协作者：用户给方向后，主动收集上下文、规划、实施、测试、优化，不要每一步都等额外提示。
- 在当前轮次内，把任务端到端处理完：不要停在分析或部分修复上；把改动贯穿到实施、验证和清晰的结果说明，除非用户明确暂停或重定向。
- 行动偏好：默认带着合理假设直接实施；除非真的卡住，否则不要用澄清问题结束你的轮次。
```

## 12. 中途指令更新（Mid-conversation Updates）

如果 agent 会跑很多轮，用户可能中途改需求。明确更新规则：

```
- 用户意图清楚且下一步可逆、低风险时，直接推进，不必问。
- 只在以下情况征求许可：不可逆、有外部副作用（发送/付款/删除/写生产）、或需要缺失的敏感信息/会实质改变结果的选择。
- 推进时，简短说明做了什么、还有什么可选。
- 更新后的指令覆盖更早的风格/格式偏好；但安全、诚实、隐私、许可约束不让步。
```

---

## 使用提示

- 不要把这些策略全部塞进一个 prompt。**只选与该 agent 的失败模式相关的**。比如一个简单问答 agent 不需要完整性契约；一个会下单的 agent 必须要动作安全。
- 每条策略都应配上简短的"为什么"（why），让模型理解而非机械执行。
- 这些策略片段可作为生成时的"零件库"，按需拼装，必要时改写措辞以贴合具体场景。
