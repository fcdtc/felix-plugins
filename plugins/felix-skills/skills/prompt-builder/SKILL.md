# Prompt Builder

一个交互式的 prompt 生成器。通过与用户逐轮沟通，补全构建优秀 prompt 所需的必要信息，最终产出一份结构清晰、可直接复制使用的 Agent/工具调用类 prompt。

设计依据：OpenAI 官方 Prompt Guidance 文档（覆盖 GPT-4.1 → GPT-5.5 的提示工程最佳实践），提炼跨模型通用的原则。

## 核心原则（生成 prompt 时必须内化）

这些原则来自 OpenAI 官方文档，是判断"什么是一个好 prompt"的标尺。生成时请始终遵循：

1. **结果导向，而非过程堆砌** —— 描述"成功长什么样"，把路径选择留给模型。旧式 prompt 喜欢规定"先做 A 再做 B 再做 C"，对现代模型这只会收窄它的搜索空间、让它变得机械。除非每一步都真正必需，否则不要写死流程。

2. **停止条件必须显式** —— 这是最容易被遗漏、却最影响 Agent 质量的部分。明确告诉模型：什么时候该停止、什么时候该重试、什么时候该放弃、什么时候该问用户、什么时候该调用工具。没有停止条件的 agent 要么过早终止，要么无限循环。

3. **慎用绝对词** —— `ALWAYS`/`NEVER`/`必须`/`只能` 只用于真正的硬性不变量（安全规则、必填字段、绝不能发生的动作）。对于"什么时候搜索/什么时候提问/什么时候用工具"这类判断题，用决策规则（decision rules）替代绝对命令。这是文档反复强调的一点。

4. **工具规则要具体（仅工具型 agent）** —— 只当 agent 真的会调用工具/函数时才需要这一节：每个工具做什么、何时用、何时不用、参数从哪来、调用后如何确认。非工具型 agent（纯对话/写作/分析）不要凭空加工具章节，否则会引入幻觉和乱调用的风险。

5. **输出契约要锁死** —— 明确输出的结构、长度、格式（JSON/Markdown/纯文本）、语气、分段。Agent 越是面向产品，输出格式越要稳定。

6. **缺失信息的行为要定义** —— 当关键信息缺失时，模型应该：(a) 用工具检索，(b) 问一个最小化的澄清问题，还是 (c) 标注假设后继续？不说清楚，模型就会猜——而猜测是 agent 失败的头号原因。

7. **必须定义"止损"边界（Error Handling）** —— 哪些情况模型应该**停下来问用户**，而不是硬着头皮往下做。核心判断：一个错误如果**不可逆、影响外部、或继续做下去可能放大损失**（写脏数据、花钱、发消息、删东西、覆盖文件、调用付费 API），就必须暂停提问；反之，可重试、纯本地、低代价的错误（格式不符、单次检索失败、临时解析错误），模型应自行重试或回退，不打扰用户。把"什么时候该停"写明白，比写"出错了请处理"有效得多。

8. **格式服务理解** —— 默认用自然的段落和短句；列表、标题、表格只在确实提升可读性时使用。不要让结构比内容更重。

9. **解释 why，而不是堆 MUST** —— 现代 LLM 很聪明。给出理由比堆叠命令更有效。如果发现自己在大写 `ALWAYS`，停下来想想能否用"因为 X，所以倾向于 Y"来重写。

更细的版本化策略（按场景）见 `references/` 下的文档，按需加载。

## 工作流程

生成分三步走。**严格按顺序执行**，不要跳步。

### 第一步：意图澄清

先理解用户想做什么。如果用户一开始的描述就够完整，可直接进入第二步收集剩余信息。通常需要先确认：

- **任务本质**：这个 prompt 要驱动一个什么类型的 agent？（客服 / 编码 / 研究 / 数据处理 / RAG / 通用助手 / 其他）
- **目标模型/平台**：将跑在哪个模型或产品上？（不同模型对 prompt 的敏感度和最佳实践有差异。如果是 OpenAI 模型，可参考 references；其他模型，套用通用原则）
- **一次性还是多轮**：是单轮问答，还是要持续多轮对话/长流程执行？

如果用户描述模糊（比如"帮我写个客服 prompt"），先用 1-3 个问题锁定方向，再进入第二步。

### 第二步：结构化信息收集（核心）

这是生成优秀 prompt 的关键。用 `AskUserQuestion` 工具，按下面的"必要信息清单"一次性或分批收集。**不要让用户一次性回答 10 个问题**——按主题分组，每轮 2-4 个高价值问题。

**收集过程中，凡是影响 prompt 走向的关键判断点不清楚，就停下来问**——比如"这个错误该不该惊动用户""输出给谁看""算不算完成"，这些一旦猜错整个 prompt 就跑偏。**判断标准**：会改变 prompt 结构或核心行为的，问；只是措辞细节、用户没答也能合理默认的，用 `[假设：...]` 标注后继续，别为小事反复打断用户。

#### 必要信息清单

| 维度 | 要问清楚的事 | 为什么重要 |
|---|---|---|
| **角色与人格** | agent 扮演谁？语气如何（直接/温暖/正式/简洁）？面向谁？ | 决定 agent 的声音和协作方式 |
| **核心目标** | agent 最终要交付什么用户可见的结果？ | 这是 prompt 的北极星，其余都服务于它 |
| **成功标准** | 什么算"完成"？必须满足哪些条件才能给出最终答案？ | 没有它，agent 不知道何时停；这是停止条件的基础 |
| **可用工具**（仅工具型 agent） | 有哪些工具/函数/能力？各自何时用？参数从哪来？ | 工具型 agent 质量的核心杠杆；非工具型 agent 跳过此行 |
| **约束** | 有哪些硬性限制？（安全、业务、数据、副作用、权限边界） | 这些才是该用"绝不/必须"的地方 |
| **输出格式** | 结构、长度、分段、格式（JSON/Markdown/纯文本）、语气 | 锁死输出契约，保证产品可用 |
| **停止与回退规则** | 何时重试？何时回退？何时放弃？何时问用户？何时停止？ | 最易遗漏、影响最大的部分 |
| **错误处理 / 止损边界** | 哪些错误必须**停下来问用户**（不可逆、影响外部、花钱、写脏数据、删改、发消息）？哪些可自行重试或回退（可逆、纯本地、低代价）？ | 防止 agent 把小错滚成大事故；和"停止条件""缺失信息"不同——这里关注的是"错误该不该惊动人" |
| **缺失信息处理** | 关键信息缺失时，检索 / 提问 / 假设，哪种？ | 防止 agent 瞎猜 |

每收集一批，用你自己的话简短复述确认（"我理解为：X、Y、Z，对吗？"），确保没跑偏。用户说"对"或补充后，继续下一批。

对于用户没明确回答的维度，不要空着——用合理默认值填充，并在最终 prompt 里用 `[假设：...]` 标注，提醒用户事后复核。默认值参考 `references/defaults.md`。

### 第三步：生成 prompt

信息收齐后，按下面的**标准结构**生成。每一段保持简短——只在能改变模型行为的地方加细节。

#### 标准 prompt 结构（OpenAI 官方推荐，跨模型通用）

```
Role: [1-2 句定义模型的角色、上下文、职责]

# 人格
[语气、风格、协作方式]

# 目标
[用户可见的最终结果]

# 成功标准
[给出最终答案前，哪些条件必须为真]

# 约束
[政策、安全、业务、证据、副作用方面的限制]

# 工具使用（可选，仅工具型 agent）
[每个工具做什么、何时用、何时不用、参数来源、调用后确认。非工具型 agent 删掉此节]

# 错误处理 / 何时停下来问用户
[哪些错误不可逆/影响外部/花钱 → 必须暂停问用户；哪些可逆/低成本 → 自行重试或回退]

# 输出
[分段、长度、格式、语气]

# 停止规则
[何时重试、回退、放弃、提问或停止]
```

生成时，对照前面的"核心原则"逐条检查。完成后：

1. 把完整 prompt 放在一个代码块里输出，方便用户整体复制。
2. 在 prompt 下方，用 2-4 条要点说明**为什么这样设计**、**哪些地方最值得用户按需调整**、**有哪些 `[假设：...]` 标记需要复核**。这能帮用户理解和二次调优。
3. 主动询问：要不要针对某个维度（比如工具规则、停止条件）继续打磨？

## 生成质量自检清单

交付前，用这份清单过一遍生成的 prompt。任何一项不达标，先修再交：

- [ ] **有明确的目标** —— 读完能一句话说出这个 agent 要交付什么。
- [ ] **有成功标准** —— 明确写了"完成"长什么样，而非只写过程。
- [ ] **有停止条件** —— 至少说明何时停止/重试/放弃/提问。
- [ ] **错误处理/止损边界已定义** —— 写清了"哪些错误必须停下来问用户（不可逆/影响外部/花钱/写脏数据/删改）"，其余错误让 agent 自行重试或回退。
- [ ] **工具规则具体**（仅工具型 agent）—— 每个工具都有"何时用、何时不用"，而非一句"用工具解决问题"。非工具型 agent 跳过此项。
- [ ] **缺失信息行为已定义** —— 关键信息缺失时怎么办，写清楚了。
- [ ] **绝对词用对了** —— `绝不/必须` 只出现在真正的硬约束（安全、必填字段、禁止动作）上，判断题用的是决策规则。
- [ ] **输出契约锁死** —— 格式、长度、结构、语气都明确了。
- [ ] **没有过程堆砌** —— 没有把每一步都写死成流水账。
- [ ] **每条指令都解释了 why** —— 而不是单纯堆命令。
- [ ] **没有内部矛盾** —— 通读没有互相冲突的指令（这是导致模型行为错乱的高频原因）。

## 参考文档（按需加载）

当用户的场景或模型需要更细的策略时，阅读对应文件，不必全部加载：

- `references/defaults.md` —— 各维度的合理默认值（用户没回答时用来填充并标注 `[假设：...]`），含错误处理/止损边界的默认表述
- `references/agent-patterns.md` —— **仅工具型/多步 agent 场景**才读：工具持久性、依赖检查、并行调用、完整性契约、验证循环、研究模式等专项策略。非工具型 agent 不要加载
- `references/principles.md` —— 核心原则的详细展开与代码片段示例（含工具规则降级说明、止损/错误处理条目），便于在生成时引用更具体的措辞

## 注意事项

- **始终用中文沟通和产出**，除非用户明确要求其他语言。注意：如果目标是英文模型且追求最佳效果，可建议用户用英文写 prompt（更接近训练分布），但这只是建议，不强制。
- **不要生成测试用例或评测脚本** —— 用户只要 prompt 文本本身。如果用户主动要测试用例，再单独提供。
- **不要过度膨胀 prompt** —— 现代 prompt 越短越好。只在能实际改变模型行为的地方加指令。宁可缺一条，也不要堆噪音。
- **保留 `previous_response_id`、`phase` 等运行时集成细节** —— 这些属于工程实现，不是 prompt 内容。除非用户特别问起，不放进生成的 prompt 里。
- **遇到模糊请求先澄清，别假设过头** —— 但如果某个细节用户没回答，宁可标注 `[假设：...]` 也别让 prompt 留空或乱编。
