# Note Query Skill — 查询笔记库

把 `/Users/congfei/basic-memory/` 知识库当一张可查询的图：先吃索引层定位，再按用户意图走两条路。本 skill **只读不写**——不改笔记、不刷新索引。

## 两类查询（先认清用户要什么）

用户的问题只有两种交付物，决定走哪条路：

| 类型 | 用户要的是 | 典型问法 | 走向 |
|------|-----------|---------|------|
| **A. 定位** | **笔记本身**（一份清单） | "找一下关于 X 的笔记""我库里有没有 X""还有哪些跟 X 相关" | 不读全文，出清单 |
| **B. 回答** | **问题的答案**（笔记库当知识源） | "X 是怎么回事""X 和 Y 的区别""总结下 X""X 的原理" | 读全文，归纳出答案 + 列参考 |

判定不清时，**默认走 A**（清单是更轻、更安全的交付），并在末尾问"需要我基于这些笔记回答你的问题吗？"。

## Usage

```
/note-query [问题或关键词]
```

| 命令 | 类型 |
|------|------|
| `/note-query HNSW` | A：库里有没有讲过 HNSW |
| `/note-query 还有哪些跟向量检索相关` | A：挖同主题的笔记群 |
| `/note-query HNSW 的检索流程是怎么回事` | B：基于笔记库回答原理 |
| `/note-query 2PC 和 TCC 有什么区别` | B：对比型回答 |
| `/note-query` | 进入交互，先问用户要查什么 |

## 规范来源

笔记的标准形状、frontmatter 字段、双链结构、`## 相关笔记` 区块格式——见 [`note/vault-conventions.md`](../note/vault-conventions.md)。note-query 只读不写；需要重建索引时调用 note skill 的脚本（见下文「索引保鲜」）。

## Behavior

严格按三步走。每步的**完成标志**写明，没达成别进下一步。

### 1. 读 INDEX.md 做定位（两类共用）

**完成标志：拿到一份候选笔记标题清单。**

先 `Read /Users/congfei/basic-memory/INDEX.md`——这是降维优势所在，**它是全库导航层，不要跳过它去裸 grep 全库**（裸 grep 绕过了已建好的摘要/枢纽/标签聚类，既慢又挖不到联系）。

INDEX.md 含五个区，各有用途：

| 区 | 用来做什么 |
|---|---|
| **📂 全库目录** | 每篇一行 `[[标题]] — description摘要`。用问题对摘要做语义匹配，圈出候选 |
| **🌐 知识枢纽** | 被引用最多的 top20 节点。命中某枢纽时纳入候选池——枢纽是跨主题串联的高发地 |
| **🏷️ 按标签聚类** | top30 标签 + 笔记数。问题落入某标签域时，该标签下所有笔记都值得纳入候选 |
| **🏚️ 孤立笔记** | 无双链的孤岛。一般不相关，但用户若问"哪些笔记还没接上图谱"，这里就是答案 |
| **📈 健康度指标** | 孤立笔记率/双链密度/索引新鲜度。用户问"库最近怎么样""孤岛多不多"时直接引用 |

- 候选先按摘要匹配度排序；命中标签/枢纽的同族笔记**一并纳入**，哪怕摘要里没直接出现关键词。
- 候选过多（>10）时收敛到最相关的 5-8 篇，其余记数备查。
- **零候选** → 直接输出"库里暂无相关笔记"，建议用 `/note` 沉淀，不要硬凑。
- 发现相关笔记带 ⚠️ 矛盾标注时，清单/答案里如实呈现双方（格式见 conventions「矛盾标注」）。

### 2. 判定类型

**完成标志：明确走 A（定位）还是 B（回答）。**

按「两类查询」表判定。一句话判断：**用户要"笔记"还是"答案"**——要笔记走 A，要答案走 B。

### 3. 执行对应流程

#### 流程 A — 定位（不读全文，出清单）

**完成标志：交付一份分层的笔记清单，无多余的话。**

- 把候选分成两档：**最相关**（摘要直接命中/标题就是该主题）和**可能相关**（同标签、同枢纽、间接命中）。
- 沿双链做一次轻量扩展是允许的——若某候选的 `## 相关笔记` 或 `<!--LLM-BACKLINKS-->` 区块里出现明显更对题的笔记，补进"可能相关"。但**不读正文**，只靠 INDEX.md 摘要 + 双链区块判定。
- 输出见「输出 · A」。**克制是这一类的灵魂**：不要寒暄、不要解释为什么相关、不要总结内容——用户只要清单，给清单。

#### 流程 B — 回答（读全文，归纳答案）

**完成标志：交付一个回答用户问题的答案 + 一份参考笔记清单。**

1. **精读候选**：对候选笔记 `Read` 正文，提取与问题相关的论点。候选不够时，沿双链往下挖——重点吃两个现成通道（note/note-polish + 脚本维护好的）：
   - `## 相关笔记`：`- [[标题]] — 关联说明`（人工/skill 写的正向出链）
   - `<!--LLM-BACKLINKS-BEGIN--> … END-->` 区块：`**本文引用（→）**`（出链）+ `**引用本文（←）**`（全库扫出的入链）
   - **最多 2 跳**，防雪崩；每跳回 INDEX.md 确认邻居 description 真的相关才展开。
2. **归纳答案**：综合读到的内容，**直接回答用户的问题**。答案要有结论、有依据，不是把笔记内容原样堆砌。笔记之间有矛盾或不同观点，如实呈现。
3. **罗列参考**：答案下方列出**实际用到的**笔记（不是全部候选——只列答案里真引用了论点的那些），标 wikilink 方便用户查证。
4. 挖到**意外关联**（leading word：**意外关联**）——两篇看似无关的笔记因共享标签/同被枢纽引用而印证了某个观点——可在答案里点名，说清为什么是联系。这是本 skill 超越单篇检索的价值点，但只在真有料时点，不为凑数。

## 输出

### A — 定位（极简清单）

```
**最相关**

- [[标题]] — {description 摘要}
- [[标题]] — {description 摘要}

**可能相关**

- [[标题]] — {description 摘要}
```

- 就这些。不要"✓ 找到 N 篇"、不要寒暄、不要解释。
- 每条带 description 摘要（来自 INDEX.md），让用户一眼判断要不要点开。
- 两档都可为空：没有"可能相关"就省掉那一节；全空就说"库里暂无相关笔记，建议 `/note` 沉淀"。

### B — 回答（答案 + 参考）

```
{直接回答用户问题的正文，有结论有依据}

## 参考

- [[标题]] — {这篇贡献了什么论点}
- [[标题]] — {这篇贡献了什么论点}
```

- 答案部分正常写，像在回答一个知识问题；笔记库是你的知识源，不是你要复述的对象。
- 参考清单**只列答案实际引用的笔记**，每条一句话说它贡献了什么，方便用户溯源。
- **绝不臆造**：笔记库里没有的，直说"库里暂无相关内容"，不要用自己的知识冒充笔记库的内容；区分不清时明说"这部分笔记库未覆盖，以下为一般性补充"。
- 答案若主要靠某 1-2 篇，参考清单可以短；综合了多篇就都列上。

## 索引保鲜

INDEX.md 由 `note/scripts/build-index.sh` 自动生成。**正常查询不用动它**。仅当怀疑索引过时（比如刚 `/note` 沉淀了新笔记却查不到）时，提示用户重建：

```bash
bash /Users/congfei/.claude/skills/note/scripts/update-wiki.sh
```

重建是写操作，归 note skill 管；note-query 只读，不主动跑。

## 边界

- **只读**：不修改、不新建、不重命名任何笔记；不调用 update-wiki.sh。
- **不臆造**：所有标题/路径/摘要/论点都必须来自 INDEX.md 或实际 `Read` 到的笔记内容。类型 B 尤其注意——别用模型自身知识冒充笔记库内容。
- **A 不读全文**：定位型只靠 INDEX.md + 双链区块，是否深读由用户决定。
- **B 有引用**：回答型每个论点都要能溯源到某篇笔记，参考清单不虚列。
- **不无限展开**：双链最多 2 跳，候选最多 5-8 篇，避免把全库牵进来。
