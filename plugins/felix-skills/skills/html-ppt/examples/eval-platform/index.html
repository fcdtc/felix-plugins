亮点 1 · 零回归隔离架构

一份代码、一个开关，
生产业务 0 行删除。

没有 fork 一份代码，没有独立二进制。EVALSVR=1 环境变量 + 4 层隔离，线上 main() 一字不变。

main.go
if evalEnabled() {
    config.SetEvalConfigKeysOnly() // 配置白名单
}
config.InitConfig("tconf")
if evalEnabled() {
    runEvalMode(server) // 只注册 eval 模块
    return
}
// ↓ 开关关闭，下面线上逻辑一字不变
workSvrCloseFn := registerService(...)

① 进程级开关

evalEnabled() 命中走 runEvalMode，只注册 eval 模块

② 配置白名单

SetEvalConfigKeysOnly 跳过框架缺失 key panic

③ 声明式服务路由

trpc_go.yaml 只声明 EvalSvr，未声明自动跳过

④ 独立命名空间

biz=eval · evallab.* · 与线上 worksolo 零共享

价值话术：隔离不靠"写两套代码"，靠"开关+命名空间"——线上永远安全，评测随时起。这页是整个平台最硬的技术决策。

亮点 2 · Config 层 Overlay 分流

配完即生效，
且不碰 runtime 主链路。

怎么让 CreateAgent 写库的配置运行时立刻生效，又不动 buildAgent？解法 = 在 config 层分流。

8 overlay 字段 逐字段判空覆盖 -1 哨兵 = 不覆盖 禁止 import repo (避免 cycle)

buildAgent 根本不知道 DB 的存在——它只认 config。这就是"最小侵入"的精髓。

config/agent_config.go
func GetAgentConfigByLang(ctx, agentID, lang) {
    if evalEnabled() {              // 开关
        if cfg := getAgentConfigByLangEval(
            ctx, agentID, lang); cfg != nil {
            return cfg           // DB overlay 命中
        }
    }
    return getAgentConfigByLangFromMap(...) // 回退
}

// 裸 SQL 直查 + mergeAgentOverlay 逐字段覆盖 yaml
分流点放在 config 层而非 runtime——dynamic.go buildAgent 主流程零改动。8 个字段：system_prompt/tools/model_name/skill_biz/allowed/excluded/force_inject/exclude_system_skill。

亮点 3 · 请求级 Agent 切换

一次对话，
动态切换 Agent 配置。

DynamicAgent 的 agent_id 构造时写死，AG-UI 请求怎么切换？请求级覆盖 + 硬门控。

▸ forwardedProps.agent_id → RuntimeState
▸ effectiveAgentID(ctx) 请求级读取
▸ 首行硬门控：非 eval 恒 d.agentID
▸ 仅锁 3 读点：buildAgent/resolveBiz/resolveSkills
▸ agent 不在 registry → work_agent 兜底 merge
dynamic.go
func (d *DynamicAgent) effectiveAgentID(ctx) {
    if !config.EvalEnabled() {
        return d.agentID   // ← 零回归硬门控
    }
    if reqID, ok := getRuntimeState(
        ctx, requestAgentIDKey); ok && reqID != "" {
        return reqID        // 请求级覆盖
    }
    return d.agentID
}
没改 runtime 核心装配逻辑，靠一个 eval 门控方法，把"请求级切换"这种重型能力变成纯增量。单测 4 例固化契约。

亮点 4 · 部署范式 + 能力复用

踩出来的硬经验，
沉淀成可复用范式。

外部可达接口标准范式

平台只为 trpc_go.yaml 声明的 tRPC service 分配端口 + 外部映射。裸 net/http / 自建 mux 都拿不到映射。

✦ proto 桩方法 ✦ trpc_go.yaml 声明 service ✦ registerService + RegisterXxx ✦ service/api/logic 三层

SkillHub / AgentHub / GetTrace / GetRunAssets 全复用此范式，新增接口零新增 service/端口。

横向复用生产 runtime 能力

"复用 runtime 不改 runtime"——线上一票横切能力原生复用：

▸ Venus-Session-Id 请求头（会话级缓存/审计）
▸ Anthropic Prompt Cache 4 断点（省 token）
▸ session mysql + 异步摘要器
▸ langfuse 全链路埋点（4 层 span）
这页体现工程沉淀：不只是做出来，还把踩坑经验固化成范式，后续新增能力成本极低。

// 工程纪律

三条铁律，
贯穿每行改动。

① 不侵入业务

开关 / 配置 / 嵌入复用，非删改主链路。

② 复用不改 runtime

隔离靠配置 + 命名空间，不靠改 runtime 代码。

③ 独立注册空间

一切 eval / evallab 标识，与线上零共享。

结果 ▸ 开关关闭时线上逻辑一字不变，所有 eval 能力都是纯增量分支——可灰度、可回退、零风险。

让老板放心：底子干净。每行改动都过自检清单。这是为什么敢上线、敢复用生产 runtime。
